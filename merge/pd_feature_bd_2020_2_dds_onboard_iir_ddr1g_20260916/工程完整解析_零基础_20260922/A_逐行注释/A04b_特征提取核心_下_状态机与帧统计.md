### 1.1 复位段（第 584–619 行）

⭐ **第 597 行 `last_trig <= {TS_W{1'b1}}`（全 1 = 最大值）是一个细致的初始化技巧**：

- 目的是**保证第一个事件不会被死区抑制**；
- 若初值是 0，第一个事件的 `dt_gap = h_ts`（时间戳还小的时候），会被误判为"距上次触发太近"而被丢掉。

### 1.2 每拍无条件执行的输出清零（第 620–645 行）

```
620        end else begin
621            ev_tvalid    <= 1'b0;
622            ev_tlast     <= 1'b0;
623            prpd_we      <= 1'b0;
624            st_meas_done <= 1'b0;
625            st_apply_done <= 1'b0;
```
⭐ **这就是"单拍脉冲"的标准生成方式**：每拍先把这些输出清 0，只有特定状态才把它们置 1。于是它们必定是**干净的 1 拍脉冲**。
- ⚠️ **注意 `ev_tdata` 没有清零**（只有 `ev_tvalid` 清了）。这是**有意的**：数据与 `tlast` 只在发事件时更新，其余时间保持。**AXI-Stream 的约定是"数据只在 `tvalid` 为 1 时被采样"**，所以保持旧值无害且省逻辑。✓

```
626            // frame_valid/overflow 显式确认（契约 v3.0 §5.4）：
627            //   FRAME_STAT(0x44) 只读，不再读清；由 FRAME_ACK(0x48) 的
628            //   bit0 / bit1 分别清 frame_valid / overflow。
629            if (cfg_frame_ack)     st_frame_stat[0] <= 1'b0;
630            if (cfg_frame_ovf_ack) st_frame_stat[1] <= 1'b0;
631            // APPLY: 只登记请求, 真正的换档在周期边界 S_CYC 完成
632            if (cfg_apply) apply_pending <= 1'b1;
```
⭐ **第 626–630 行解释了一次重要的接口契约修正**：
- **旧语义**：读 `FRAME_STAT`（`0x44`）就清 `frame_valid`（"读清 / read-clear"）。
- **问题**：PS 的读流程是"读 `FRAME_ID` → 读数据 → 再读 `FRAME_ID` 比对一致性"。**如果中途被中断重入**，`frame_valid` 已经被第一次读清掉了，第二次比对就没意义了 —— **"复读 ID 比对"的一致性读流程无法实现**。
- **新语义**：`FRAME_STAT` 改成**只读**；改用 `FRAME_ACK`（`0x48`）**显式写 1 确认**。
- ⭐ **可复用教训：`read-clear`（读即清）这种"带副作用的读"在多步读序列里非常危险**，应改为显式 ack。
- `cycle_idx` 却仍是"读不影响"的（它只在 `S_CYC` 自增），所以可用作一致性比对的锚点。

```
634            if (win_lost) begin
635                st_overflow <= 1'b1;
636                // 注意: win_lost 是单拍脉冲, 由 sync 块在非 close 拍自动清零,
637                //       此处不再清零, 避免与 sync 块 multi-driven。
638            end
```
- ⭐ **这里再次体现"一个 `reg` 只能一个 `always` 驱动"的纪律**：`win_lost` 由采集块驱动，本块**只读不清**。注释明确写出理由 —— 这是从 `frame_ad_max_acc` 那次 multi-driven 事故里学到的教训（见上篇 5.5）。
- ⭐ **`st_overflow` 是"粘滞（sticky）"的**：一旦置 1 就一直保持（直到软复位）。**为什么？** 因为丢窗是**稀疏的瞬时事件**，如果只是 1 拍脉冲，PS 轮询根本抓不到。
- ⭐ **"异步事件必须粘滞后再给软件轮询"** 是本工程反复出现的原则：`pd_ddr_ring_wr.v:433-435`（上游溢出）、`:428-432`（DataMover 错误）、`pd_ddr_snap_copy.v:146-150`（拷贝错误）都用了同一手法。

641            // 否则首个周期统计包会把预热期的脉冲一并计入 n/I/P。
642            if (arm_clr) begin

```
- "上膛"时清 `cyc_n`/`cyc_qmax`（**周期内**计数），防止预热期数据污染首周期。
- ⚠️ **注意只清了周期级计数，没有清 `acc_n`/`acc_sum_abs_q` 等全局累加器** —— 因为全局累加器要跨周期累积，本来就不该在这个时刻清。✓

## 2. 状态机逐状态解析（第 647–898 行）

主结构是 `case (fsm) ... endcase`。下面逐个状态展开。

### 2.1 `S_IDLE`（第 649–652 行）

```
649                S_IDLE: begin
650                    if (fsm_take_win)      fsm <= S_PEAK;
651                    else if (fsm_take_cyc) fsm <= S_CYC;
652                end
```
- 空闲时检查两个 pending，**窗口优先**（与第 210–211 行的定义一致）。
- 若两者都没有，`fsm` 保持 `S_IDLE`（因为 `case` 里没有 `else`，`fsm` 不变）。

### 2.2 `S_PEAK`（第 655–670 行）—— 第 0 级流水：一次性锁存 12 个量

```
655                S_PEAK: begin
656                    // 第 0 级流水: 采样由 h_max/h_min/sin_q 组合派生的中间量
657                    q0_sgn_r  <= q0_sgn;
658                    q1_sgn_r  <= q1_sgn;
659                    u_val_r   <= u_val[17:0];        // 截断高位: 值域内高位恒为符号扩展, 无损
660                    gate0_r   <= gate0;
661                    gate1_r   <= gate1;
662                    dead_ok_r <= dead_ok;
663                    h_ph_r    <= h_ph;
664                    h_ts_r    <= h_ts;
665                    q0_pol_r  <= q0_pol;
666                    q1_pol_r  <= q1_pol;
667                    amp0_r    <= amp0;
668                    amp1_r    <= amp1;
669                    fsm       <= S_Q1;
670                end
```
- **这一拍一次性锁存 12 个量**，全部来自"本窗口已稳定的值"：
  | 寄存器 | 来源 | 用途 |
  |---|---|---|
  | `q0_sgn_r`/`q1_sgn_r` | `q0_sgn/q1_sgn`（模式相关转换后的带符号幅度） | 下一步乘法 |
  | `u_val_r` | `u_val[17:0]`（电压瞬时值） | `q × u` |
  | `gate0_r`/`gate1_r` | 门限判决 | 是否发事件/统计 |
  | `dead_ok_r` | 死区判决 | 是否统计 |
  | `h_ph_r` | 相位窗号 | 事件包 + PRPD 地址 + 剔除判定 |
  | `h_ts_r` | 时间戳 | 死区计算 |
  | `q0_pol_r`/`q1_pol_r` | 极性 | 事件包 + 12 档计数 |
  | `amp0_r`/`amp1_r` | ADC 码幅度 | 12 档门槛比较 |
- ⭐ **锁存之后，后续拍就不再依赖 `h_max/h_min/sin_q` 这些"可能被新窗口更新"的信号** —— 这就是**"输入隔离"**，也是"流水线语义不变"的保证。
- 第 659 行 `u_val[17:0]`：截取低 18 位。注释论证"值域内高位恒为符号扩展，无损"—— 依据是上篇 5.6 的 18 bit 值域推导。✓
- **注意本状态没有 `if (ev_tready)` 门控** —— 因为这一拍不发事件，纯粹是内部寄存，不需要等下游。

### 2.3 `S_Q1`（第 673–678 行）—— 第 1 级流水：乘法

```
673                S_Q1: begin
674                    // 第 1 级流水: 幅度 x 标定系数 (DSP48E1, 内部流水寄存器)
675                    q0_mul_r <= q0_sgn_r * $signed({1'b0, cfg_scale});
676                    q1_mul_r <= q1_sgn_r * $signed({1'b0, cfg_scale});
677                    fsm      <= S_Q2;
678                end
```
- 两个乘法：`14 bit × 17 bit → 32 bit`，综合成一个或两个 DSP48E1。
- `$signed({1'b0, cfg_scale})` 把 16 bit 的 `cfg_scale` 零扩展成 17 bit 有符号（保证正数、且有符号乘法）。
- ⚠️ **【观察】** `cfg_scale` 按**无符号**解释 ⇒ "标定系数"只能非负。默认 256（Q8.8 的 1.0）✓。若 PS 想用负系数（理论上不该有），会被解释成一个大正数。
- ⚠️ **【观察】** 两个乘法**同时**用同一个 `cfg_scale`，若综合器把它们映射到两个 DSP48，则这一拍有两级乘法器并行。**这解释了为什么本模块的 DSP 用量是"每通道 2 个"**（加上 `q×u` 那个是 3 个，但 `q×u` 在 `S_ACC` 拍用，可以复用）。

### 2.4 `S_Q2`（第 681–690 行）—— 第 2 级流水：量化 + 绝对值

```
681                S_Q2: begin
682                    // 第 2 级流水: 量化 (sat16) + 绝对值同步预寄存。
683                    // q0_pc_r 与 abs_q0_r 由**同一组合值** q0_pc_n 载入 → 严格同拍，
684                    // 不存在"非阻塞赋值读到旧一拍"的错位（原顾虑已由同源载入规避）。
685                    q0_pc_r  <= q0_pc_n;
686                    q1_pc_r  <= q1_pc_n;
687                    abs_q0_r <= q0_pc_n[15] ? (-q0_pc_n) : q0_pc_n;
688                    abs_q1_r <= q1_pc_n[15] ? (-q1_pc_n) : q1_pc_n;
689                    fsm      <= S_ACC;
690                end
```
- `q0_pc_n = sat16(q0_mul_r >>> 8)`（第 435 行）是**组合**值。
- 第 685–688 行：**四个寄存器都由同一拍的两个组合值载入** → 严格同拍。这正是上篇 5.6 第 450–455 行那段优化的落地实现。
- 第 687 行 `q0_pc_n[15]` 是 16 bit 有符号的符号位；为负则取负得到绝对值。
- ⚠️ **【观察】** `abs_q0_r` 声明为 `[15:0]` **无符号**。若 `q0_pc_n = −32768`（16 bit 有符号最小值），`−q0_pc_n` 在补码里仍是 `0x8000`，按无符号解释 = **32768** —— 恰好是正确结果 ✓。但这种"靠无符号解释侥幸正确"的写法很脆弱：若下游把它当有符号用就会出错。

### 2.5 `S_ACC`（第 693–721 行）—— 发正峰事件 + 累加

```
693                // S_ACC: 原 S_PEAK 的动作 (发正峰事件 + 累加 q0), 现在用流水结果
694                S_ACC: begin

```
⭐ **整个 `S_ACC` 被 `if (ev_tready)` 包裹** —— 这意味着**下游（事件 FIFO）没准备好时，状态机会停在这里等**。
- **为什么必须等？** 这一拍要发事件（更新 `ev_tdata`/`ev_tvalid`）。不等就更新会丢事件。这是标准 AXI-Stream 握手：**源只能在 `tvalid & tready` 同时成立时推进**。
- ⭐ **代价（也是设计意图）**：若下游长期不 ready（FIFO 满），状态机会卡住 → `win_pending` 积压 → 丢窗 → **`st_overflow` 置位**。**这正是 `st_overflow` 的设计用途：把"下游背压导致的丢窗"变成可观测的标志。**

```

- **发事件条件**：`(gate0_r || cfg_ev_all) && keep_ev0`
  - `gate0_r`：幅度超门限；或 `cfg_ev_all`（调试用，绕过门限）；
  - **且** `keep_ev0`：不在剔除区内（v2 功能）。
- 第 699 行：事件序号自增。注释说"与累加器并行，不入关键路径" —— 它是独立的 25 bit 加法器，不依赖幅度/门限链，所以不构成关键路径 ✓。

### 2.7 `S_STAT`（第 758–816 行）—— 12 档门槛计数 + 帧合计

⭐ **这 11 行注释定义了 12 档计数的完整规则**，必须理解透：

1. **计数对象**：只统计"合格放电事件"，即已经通过
   - 基本门槛 `cfg_thresh`（`gate0_r`/`gate1_r`），
   - 死区去重（`dead_ok_r`），
   - 剔除区判定（`keep_stat0`/`keep_stat1`）

2. **分档规则**：幅度 ≥ 档位门槛时该档 +1；**6 档相互独立，一次事件可同时命中多档**（即档位是"≥"关系不是"区间"关系）。所以这 6 个计数**不是直方图分段**，而是"累计计数（cumulative count）"。

3. **`档位门槛 = 0` 表示该档停用**（不统计）。所以不能用"0 门槛"来表达"所有脉冲都算" —— 要用 1。

5. ⭐ **不设回差（hysteresis）的理由**：死区 `cfg_deadtime` 已经完成了"同一脉冲跨窗"的去重；**在"窗口峰值域"再叠加回差会造成永久漏计** —— 因为峰值流不是连续信号，触发后**没有"低于释放阈的采样点"去重新上膛**（每个窗口只输出一个峰值，要么超阈要么不超阈，不存在"回升再下降"的过程）。**这是一条从"信号形态"出发的正确推理**，值得学习。

### 2.8 `S_PRRD`（第 819–828 行）与 `S_PRWR`（第 831–837 行）—— PRPD 读改写

- ⭐ **第 820–821 行的注释说明了"兜底落账"的作用**：
  - **ABSMAX/PP 模式**：走 `S_ACC → S_STAT → S_PRRD`，如果 `S_ACC` 置了 `qu_acc_v`，`S_STAT` 拍不处理它，所以**这一拍必须累加**；
  - **POSNEG 模式**：走 `S_ACC → S_PEAKN → S_STAT → S_PRRD`，`S_PEAKN` **已经累加过**并清了 `qu_acc_v`，所以这一拍 `qu_acc_v = 0`，不会重复累加。
  - ⭐ **这是一个"覆盖所有路径"的兜底设计**：与其在每条路径上都精确判断"该不该累加"，不如在公共的最后一拍统一检查。**代价是需要一个 pending 标志（`qu_acc_v`）。**
  - ⚠️ **【隐藏风险】** 若 `qu_acc_v` 因为某种原因**被置 1 但没有被清**（例如下游长期不 ready 导致状态机停在 `S_ACC` 又被复位），这个乘积会在下一轮处理时被重复累加。当前设计中 `qu_acc_v` 只在 `S_PEAKN`/`S_PRRD` 里被清，且这两拍一定会在 `S_ACC` 之后到达 ✓。**但要注意 `S_ACC` 里的 `qu_acc_v <= 1'b1` 是在 `if (ev_tready)` 内**，若 `ev_tready` 一直为 0，`qu_acc_v` 不会被置 1，也就不会累积 —— 一致 ✓。
- 第 826 行 `prpd_addr <= h_ph_r`：**给出 PRPD 读地址**。因为 BRAM 是同步读、1 拍延迟，所以下一拍（`S_PRWR`）`prpd_rdata` 才有效。

⭐ **这段是"哨兵值语义"的漂亮应用**：
- `frame_ad_max_acc` 的初值是 `SMIN`（哨兵）。若整帧从没有效样本，它仍等于 `SMIN` → **输出 0 而不是 −2048**（避免把哨兵当真实极值上报）。
- 否则把 12 bit 有符号**符号扩展**成 16 bit：`{{16-ADC_W{符号位}}, 值}` = 复制 4 份符号位（因为 `16-12 = 4`）。
- 第 862 行同理（`SMAX` 作哨兵）。
- ⚠️ **【观察 · 潜在歧义】** 若某一帧的**真实最大 AD 码恰好等于 +2047**（`SMAX`），那么 `frame_ad_min` 可能与哨兵混淆…… 不，注意：
  - `frame_ad_max_acc` 的哨兵是 `SMIN`（−2048），`frame_ad_min_acc` 的哨兵是 `SMAX`（+2047）。
  - 所以"`frame_ad_min_acc == SMAX`"既可能是"没有效样本"，也可能是"真实最小值恰好为 +2047"。

### 2.10 帧内 AD 包络累积（第 900–913 行）—— 块外的"尾巴"

```
900            // -----------------------------------------------------------------
901            // 帧内 AD 包络极值累积（2026-09-10 从窗口块 block1 移入本块 block2）
902            //   移入原因: frame_ad_max_acc / frame_ad_min_acc 原先同时在 block1
903            //             与本块被赋值 → 综合报 [Synth 8-6859] multi-driven net
904            //             (2nd driver = VCC)，AD max/min 功能失效。
905            //   位置: 本块内、case 之后 → 本块成为这两个 reg 的唯一驱动源。
906            //   优先级: 与帧末清零(S_CYC 分支)同拍时，本处赋值在后 → 窗口更新优先，
907            //           末窗数据不丢失（顺延计入下一帧快照）。
908            //   语义保持: 全窗口参与（含无放电噪声窗），与放电事件解耦。
909            // -----------------------------------------------------------------
910            if (win_close) begin
911                if ($signed(wc_max) > frame_ad_max_acc) frame_ad_max_acc <= wc_max;
912                if ($signed(wc_min) < frame_ad_min_acc) frame_ad_min_acc <= wc_min;
913            end
```
⭐ **这段是"ulti-driven 事故修复"的最终落地**，注释把三件事说透了：

1. **为什么移到这里**：原代码在"窗口锁存块"和"帧块"都赋值 → multi-driven。移入本块后，**本块成为这两个 `reg` 的唯一驱动源**。
2. ⭐ **优先级（最关键的一点）**：
   - 本段在 `case` 语句**之后**，所以同一拍里"本段赋值"**晚于** `S_CYC` 分支里的"帧末清零"；
   - Verilog 规则：**后写者胜**；
   - 所以 **`S_CYC` 那拍的 `frame_ad_max_acc <= SMIN` 会被本段覆盖**（如果这拍恰好 `win_close` 为 1）；
   - 效果：**末窗数据不丢失，顺延计入下一帧快照**。
   - ⭐ **这是一个"故意利用语句顺序来定优先级"的写法。** 它正确但**非常依赖阅读者对 Verilog 语义的精确掌握**。更好的工程做法是显式写出优先级判断（例如 `if (!cyc_end)` 包裹），或至少在注释里写清。**本工程选择了注释写清的方式。**
3. **语义**：全窗口参与（含无放电的噪声窗），与放电事件解耦 —— 这样"某帧一次放电都没有"也能给出 AD 边界。

⭐⭐ **本节的核心教训（值得反复看）**：
- **一个 `reg` 只能有一个 `always` 块驱动**；
- **同一块内多次赋值按书写顺序决定优先级**；
- **用书写顺序表达优先级虽然有效，但可读性差，必须配注释**；
- **改代码时如果挪动了代码块的位置，优先级可能被静默改变** —— 这是本工程里最容易引入隐蔽 bug 的操作之一。

## 3. 状态机全路径梳理（读懂这张表，就掌握了整个模块）

设 `M = PC`（普通时钟）、`E = ev_tready`。

| 触发 | 状态序列 | 说明 |
|---|---|---|
| 有窗口待处理（`win_pending`）、`cfg_mode = ABSMAX` | `S_IDLE → S_PEAK → S_Q1 → S_Q2 → S_ACC → S_STAT → S_PRRD → S_PRWR → S_IDLE` | **8 拍**（每拍需 `ev_tready` 的状态是 `S_ACC`） |
| 同上，`cfg_mode = PP` | 完全同上 | 唯一的差别是 `q0_code = q_pp_r`、`q0_pol` 恒 POS |
| 同上，`cfg_mode = POSNEG` | `S_IDLE → S_PEAK → S_Q1 → S_Q2 → S_ACC → S_PEAKN → S_STAT → S_PRRD → S_PRWR → S_IDLE` | **9 拍**（多一个 `S_PEAKN`），可能发 2 个事件 |
| 有周期待处理（`cyc_pending`）且无 `win_pending` | `S_IDLE → S_CYC → S_IDLE` | **2 拍**，发 1 个统计包（`tlast=1`） |

**时序预算校核（26 MSPS 场景）**：
- 一个窗口约 508 个样本 = 508 个 `adc_dv` 拍；
- 每次窗口处理最多 9 拍；
- 所以处理开销占 `9/508 ≈ 1.8%`，**余量极大** ✓。
- **瓶颈不在状态机，而在事件 FIFO 的深度与下游 `tready`**（若 FIFO 满 → `S_ACC`/`S_CYC` 卡住 → 丢窗）。

## 4. 本篇易错点小结

1. **`S_ACC` / `S_PEAKN` / `S_CYC` 三个状态都被 `if (ev_tready)` 包裹**：下游不 ready 会导致状态机卡住 → 丢窗（`st_overflow`）/ 帧统计停摆。**这是"丢窗"的主要来源，不一定是 PL 逻辑错。**
2. **`last_trig` 初值是全 1**（不是 0），目的是让第一个事件不被死区误抑制。
3. **档位门槛换档只在 `S_CYC` 执行** → **若没有工频同步信号，`st_apply_done` 永不置位，"配置已生效"无法证明。**
4. **`st_sn_*` 是"自上次清零以来的全局累计"**，而统计包里的 `cyc_n`/`cyc_qmax` 是"本周期"。**两者语义不同，别混。**
5. **`st_sn_*` 与 `acc_*` 的清零在同一拍**，靠非阻塞赋值"读旧值"保证快照正确 —— 这是刻意设计，不是巧合。
6. **`st_frame_stat[1]`（丢帧）用"上一帧 `frame_valid` 还没清"来判断**，依赖非阻塞赋值读旧值。
7. **`st_overflow` / 帧 `overflow` / DataMover `o_err` 都是粘滞位**（因为是稀疏瞬时事件，必须粘滞才能被软件轮询抓到）。
8. **`st_pos_cnt` 是"累计计数"不是"分段直方图"**：6 档门槛是"≥"关系，一次事件可命中多档。
9. **帧内 AD 包络的两个 `reg` 只在本块（`case` 之后）被驱动**，优先级靠"书写顺序"表达：`win_close` 的更新**故意**覆盖 `S_CYC` 的帧末清零，使末窗不丢。**挪动代码块位置会静默改变这个优先级。**
10. **`stat_q1_pol` 恒为 1**（因为 `q1_pol` 是常量 `PD_POL_NEG`），所以 `S_STAT` 里"q1 走正脉冲分支"的代码是**死代码**。功能正确，但读代码时要意识到。
11. **POSNEG 模式下同一窗口的正负峰各自独立走一次统计**，同拍读到的 `last_trig` 是旧值 → **窗口级死区不能区分同窗的正负峰**。这是"路线 B"的固有局限。
12. **PRPD 的"读-改-写"依赖 BRAM 的 1 拍同步读延迟**（`S_PRRD` 给地址、`S_PRWR` 用数据）。若将来改 BRAM 为 0 延迟或 2 拍延迟，必须同步改状态机。
