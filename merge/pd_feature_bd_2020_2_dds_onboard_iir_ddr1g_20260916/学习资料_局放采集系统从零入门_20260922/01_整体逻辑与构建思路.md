# 第一章：整体逻辑与构建思路

## 1. PL 与 PS 分别是什么

Zynq-7020 可以理解为一颗芯片内有两台不同类型的“计算机”。

| 区域 | 名称 | 擅长什么 | 本项目职责 |
|---|---|---|---|
| PL | Programmable Logic，可编程逻辑 | 每一个时钟周期并行处理大量硬件数据 | 采样、特征、触发、DDR 写入、快照复制 |
| PS | Processing System，ARM 处理系统 | C 程序、协议、复杂控制、网络 | 管理采集、整理记录、FFT、TCP 服务 |

PL 不是“运行 C 程序的地方”；它被综合成电路。PS 才运行 C 语言编译出来的 ELF 程序。

## 2. 本工程的数据流

```text
                         ┌───────────────────────────────┐
                         │ PL：26 MHz 采样时钟域          │
DDS 测试源 / 未来 ADC ───→│ 4 × 12-bit adc_data + adc_dv  │
                         └───────────────┬───────────────┘
                                         │
                         ┌───────────────▼───────────────┐
                         │ PL：跨时钟域与特征处理          │
                         │ pd_adc_cdc → pd_feature_core   │
                         │ 峰值、相位、PRPD、事件 AXIS     │
                         └───────┬───────────────┬───────┘
                                 │               │
                       事件包    │               │ 原始样本
                                 ▼               ▼
                         AXI DMA → DDR      pd_ddr_wr_top → DDR 环形区
                                                  │
                                      触发后复制 │
                                                  ▼
                                              快照槽 DDR
                                                  │
                         ┌────────────────────────▼───────────────┐
                         │ PS：ARM Cortex-A9                        │
                         │ pd_acquisition_core                      │
                         │ 快照解包 → 自动事件定位 → 1024 点 FFT     │
                         │ pd_tcp_service → 以太网 TCP:6001         │
                         └─────────────────────────────────────────┘
```

这里有两类结果，初学者最容易混淆：

- **事件包**：特征模块产生的小数据包，例如峰值、周期统计。它走 `pd_feature_0 → AXI DMA → DDR`。
- **快照**：触发前后的一大段原始四通道采样数据。它由 `pd_ddr_0` 自己写到 DDR，然后由 PS 复制、分析和下载。

## 3. 为什么这样划分

26 MSPS × 4 路意味着每秒有 1.04 亿个采样值。PS 不应逐点实时接收和分析，否则 CPU、缓存和总线会首先成为瓶颈。

所以设计原则是：

```text
每点必做、必须实时的工作 → PL
偶发、需要复杂算法或网络协议的工作 → PS
```

因此 CDC、触发、环形写入、快照冻结必须留在 PL；FFT、记录管理、TCP、文件下载适合在 PS。

## 4. 构建一个功能时的正确思考顺序

不要从“我要写代码”开始，而应按下列顺序：

1. **写数据契约**：位宽、符号、单位、时钟、有效信号、最大长度。
2. **画数据流**：数据从哪里来，到哪里去，谁拥有它，在哪里缓存。
3. **先定义异常路径**：满、超时、复位、DMA 错误、槽占满时怎么办。
4. **先单元验证再集成**：例如 FFT 自检先通过，才读真实快照。
5. **让软件返回可验证的文本**：例如 `seq`、`bytes`、`bin`、`crc32`，不能只打印“成功”。
6. **最后才做上位机界面**：界面只是协议客户端，不能替代底层验证。

## 5. 当前命令如何对应数据流

| TCP 命令 | 它查看或操作的对象 |
|---|---|
| `START 512` | PS 启动一次有上限的事件采集服务 |
| `STATUS` | PL/PS 当前状态、DMA 状态、DDR 状态、错误字符串 |
| `CATALOG` | PS 中保留的事件与快照序号范围 |
| `SNAP 0` | 第 0 个 PS 快照归档记录的元数据 |
| `GET SNAP 0 offset bytes` | 下载一段原始快照字节 |
| `ANALYZE SNAP 0` | 按 6 Byte/采样解出四通道原始数据，求最小/最大/平均 |
| `FFT SNAP 0 0` | 从指定快照和指定起点取 1024 点 FFT |
| `FFT AUTO SNAP 0` | 先找最大偏移点，再围绕它取 1024 点 FFT |

## 6. 本项目的第一条硬件数据契约

每一时刻的四通道 12-bit 数据被压缩成 6 Byte：

```text
Byte0 = ch0[7:0]
Byte1 = ch0[11:8] + ch1[3:0]
Byte2 = ch1[11:4]
Byte3 = ch2[7:0]
Byte4 = ch2[11:8] + ch3[3:0]
Byte5 = ch3[11:4]
```

所以：

```text
每组四通道采样 = 48 bit = 6 Byte
3,120,000 Byte / 6 = 520,000 组采样
520,000 / 26,000,000 = 0.02 s = 20 ms
```

理解这一条后，后面的 DDR 大小、快照长度、PS 解包和 FFT 窗口都能自己推导。
