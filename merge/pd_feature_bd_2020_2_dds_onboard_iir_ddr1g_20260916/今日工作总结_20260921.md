## 2. 当前系统架构与数据流

当前原型的数据主链路如下：

```text
DDS/ADC 四通道采样输入
        ↓
数字滤波模块 pd_filter_0
        ↓
局放特征提取模块 pd_feature_0
        ↓
AXI4-Stream 事件流
   ┌────┴───────────────────────────────┐
   ↓                                    ↓
AXI DMA S2MM                         自动快照触发器
   ↓                                    ↓
PS DDR 事件区                    原始数据环形缓存冻结
   ↓                                    ↓
PS 采集服务                      快照槽位管理与 DDR 复制
   ↓                                    ↓
事件归档区                       快照归档区
   └───────────────┬────────────────────┘
                   ↓
         UART 调试接口 / 后续 Ethernet 接口
```

### 2.1 PL 模块职责

| 模块/接口 | 主要职责 | 当前状态 |
|---|---|---|
| DDS 测试源 | 生成稳定、可重复的四通道测试数据 | 已用于通路验证 |
| `pd_filter_0` | 对采样数据进行数字滤波；参数由 PS 通过 AXI-Lite 下发 | 已接入并验证参数下发 |
| `pd_feature_0` | 从滤波后数据提取周期统计、峰值等局放特征 | 已实现并输出 AXI4-Stream |
| AXI DMA S2MM | 将事件流写入 PS DDR | 已验证不同长度分包 |
| `pd_ddr_0` | 原始数据环形缓冲、冻结、快照复制及槽位相关通路 | 已验证自动快照 |
| 快照槽位管理 | 管理四个快照槽、序号、长度、状态与释放语义 | 已具备自动快照服务能力 |
| ILA/调试逻辑 | 观察握手、复位、时钟及关键流状态 | 已用于硬件定位，后续需控制资源占用 |

### 2.2 PS 软件职责

PS 端负责启动和停止采集、配置滤波参数、配置自动快照、轮询 DMA 完成、解析事件数据包、归档事件和快照，并提供 UART 命令行接口。PS 不参与实时采样与特征计算，因此实时数据路径仍留在 PL，PS 侧主要承担控制、存储组织和对外通信。

## 3. 采集、DMA 与快照功能复核

### 3.1 AXI-DMA S2MM 事件接收

DMA S2MM 已能够接收局放特征模块输出的 AXI4-Stream 数据。实际运行中同时出现两类数据包：

- 周期统计类短包：典型为 8 字节、1 个 64 位 stream word；
- 峰值事件类长包：典型最大为 8224 字节、1028 个 stream word。

典型通过结果为：

```text
FEATURE_DMA_S2MM_PASS packets=128
peak_words=...
cycle_words=128
bytes_min=8
bytes_max=8224
```

该结果证明以下事项：

1. `TVALID/TREADY/TLAST` 事件流握手可完成；
2. DMA 可处理不等长包，未固定为单一 8 字节数据格式；
3. 周期统计与峰值事件可在同一 DMA 接收通路共存；
4. PS 端能够根据 DMA 传输长度和数据类型解析数据包；
5. DMA 结束状态 `DMASR=0x00001002` 对应正常完成状态。

### 3.2 自动快照与 DDR 数据复制

自动快照链路已经得到实际数据验证。特征事件触发后，硬件会冻结原始数据环形缓冲的有效窗口，由槽位管理器选择可用快照槽并完成快照复制。PS 软件读取到的典型描述符如下：

```text
SNAPSHOT slot=0 base=0x20001000 len=3120000 seq=1 flags=0x00000005
```

其中：

- `slot=0`：本次使用的硬件快照槽编号；
- `base=0x20001000`：硬件快照数据源地址；
- `len=3120000`：快照有效长度，约 3.12 MB；
- `seq`：快照序号，可用于确认多次事件是否连续发生；
- `flags=0x00000005`：快照已完成、可读取等状态标识。

PS 服务随后会把该槽位数据拷贝到软件归档区。例如：

```text
SNAP_ARCH seq=0 slot=0 src=20001000 dst=24000000 bytes=3120000
```

说明数据不仅停留在寄存器描述符层面，而是完成了从硬件快照区到 PS 归档区的实际 DDR 内存复制。

### 3.3 采集服务运行结果

本日确认过如下关键结果：

```text
ACQ_SERVICE_PASS packets=128 events=128 snapshots=1
ACQ_CLEAN_STOP ddr=00000004 slot=00080000
```

其含义为：

- DMA 采集完成 128 个数据包；
- PS 成功归档 128 条事件记录；
- 本轮采集过程中成功归档 1 个自动快照；
- 停止时 DMA、DDR 和槽位状态处于可控状态；
- 未观察到槽位丢弃异常。

需要注意，事件归档区当前容量为 16 条、快照归档区当前容量为 4 条。持续采集时会看到 `ev_ovw` 或 `snap_ovw` 增加，这表示旧归档记录被循环覆盖，是当前的软件环形归档策略，不等同于 PL 采集丢失。后续上位机协议应及时上传、确认或持久化归档数据，以避免业务层面的历史记录覆盖。

## 4. 滤波参数下发与触发行为确认

此前存在一种现象：DMA 可以正常收到周期统计包，但未必出现峰值事件和自动快照。经检查后执行滤波参数下发程序，输出：

```text
--- pd_filter_apply 26 MSPS ---
FILTER_APPLY_VERIFY_PASS
```

之后采集服务重新出现自动快照归档，表明当前 DDS 测试场景下，滤波器的系数和旁路状态会直接影响特征模块是否判定出满足条件的事件。

该结果可形成以下调试结论：

1. 当“DMA 正常但没有峰值/快照”时，不应首先怀疑 DDR 或 AXI DMA；
2. 应依次检查滤波使能、旁路状态、滤波系数、特征阈值和 DDS/ADC 输入幅度；
3. 真实 ADC 上板后，必须重新进行滤波系数、频带、触发阈值和噪声环境标定；
4. 当前 DDS 验证证明数字链路可工作，但不能直接代表真实现场局放识别率。

## 5. 时钟架构调整与约束处理

### 5.1 问题背景

启用 Ethernet0 后，PS 的 FCLK0 实际频率与原工程预期不一致。例如配置请求为 150 MHz 时，PS 侧实际给出的 FCLK0 约为 142.857 MHz。若采集系统的时钟向导继续以 FCLK0 为输入，则 130 MHz 处理时钟和 26 MHz 采样相关时钟会随之偏移。

这会带来以下风险：

- DDS 和 ADC 的样本速率不再满足原设计假设；
- 处理时钟与采样时钟的固定比例关系被破坏；
- 自定义 RTL、DMA、AXI SmartConnect 与 Block Design 的 `FREQ_HZ` 属性可能报错；
- 仿真采样率、滤波设计采样率和实际硬件采样率不再一致；
- 后续真实 ADC 的频率标定、同步和性能评估变得不可靠。

### 5.2 当前解决方案

采集主链路已改为使用 PL 板载 50 MHz 晶振作为 `clk_wiz_0` 输入：

```text
板载 PL 50 MHz 晶振（PL_GCLK）
          ↓
      pl_gclk_50
          ↓
       clk_wiz_0
       ├── 130 MHz：滤波、特征、DMA、DDR 控制和 AXI 域
       └── 26 MHz：采样相关时钟域
```

对应 XDC 的关键约束为：

```tcl
set_property PACKAGE_PIN U18 [get_ports pl_gclk_50]
set_property IOSTANDARD LVCMOS33 [get_ports pl_gclk_50]
create_clock -name pl_gclk_50 -period 20.000 [get_ports pl_gclk_50]
```

其中 `U18 + LVCMOS33` 必须与板卡原理图一致。此前看到的 `U7 + LVCMOS18` 是旧设计检查点或旧实现结果残留，不代表当前正确硬件连接。重新导入 XDC 后必须重跑综合和实现，最终应以实现后 `report_clocks`、I/O 报告与 DRC 结果确认。

### 5.3 当前时钟策略的意义

此项调整后，Ethernet0 的启用、PS PLL 改动或 FCLK0 的可实现频率变化，不再直接改变采集链路的 130 MHz 和 26 MHz 时钟。PS FCLK 可以继续用于 PS/AXI 控制相关逻辑，而采集主时序由独立的 PL 时钟源保持稳定。这是后续同时运行“采集 + DDR + 网口”的必要基础。

## 6. Ethernet0 硬件架构确认

根据核心板和底板原理图，板载以太网 PHY 为 YT8521SC-CA，Zynq PS 的 GEM0 通过 MIO 直接连接 PHY 的 RGMII 接口。当前应采用的链路为：

```text
Zynq PS GEM0
     ↓（MIO RGMII）
YT8521SC-CA PHY
     ↓
RJ45 / 网线 / 交换机 / 上位机
```

推荐且已确认的配置原则如下：

| 项目 | 配置 |
|---|---|
| 以太网控制器 | PS GEM0 / Ethernet0 |
| 数据接口 | RGMII，经 MIO 直连板载 PHY |
| RGMII MIO | MIO16–27 |
| MDC/MDIO | MIO52 / MIO53 |
| MIO Bank1 电平 | LVCMOS 1.8V |
| PHY 时钟/接口 | 遵循板载 PHY 和原理图连接 |

由于 MAC 已在 PS GEM0 中、PHY 已在板卡上，因此当前工程不需要增加以下 IP：

- AXI Ethernet；
- GMII-to-RGMII；
- 面向普通网口收发的 PL AXI DMA；
- PL 侧自定义 Ethernet MAC。

这些 IP 适合“PL 侧 MAC 直连 PHY”或“PL 侧 GMII 网络设计”。本项目使用 PS GEM0 直连 PHY，再增加它们会引入重复数据路径、额外时钟、资源占用和软件复杂度。

## 7. TTC0 与 lwIP 平台问题定位

### 7.1 TTC0 的作用

在 Vitis 创建 `lwip_echo_server` 模板时，最初出现错误：

```text
lwip_echo_server requires at least one timer hardware instance to be present
```

lwIP 的裸机 Echo Server 需要一个硬件定时器作为协议栈超时、ARP、TCP 重传和周期处理的时间基准。当前选用 PS TTC0，不需要为 TTC0 分配实际外部 MIO 引脚。

此前在 Vivado 配置界面中尝试给 TTC0 分配 MIO 时，MIO18 出现红色冲突。这是正确的警告，因为 MIO18 已被 Ethernet0 的 RGMII 数据线占用。处理原则是：

- 不修改 Ethernet0 的 MIO16–27；
- 不把 TTC0 强行分配到 MIO18；
- TTC0 作为 PS 内部外设启用即可；
- EMIO 不是 lwIP 的必要条件；即使启用 EMIO，也不应接入采集数据链路。

### 7.2 发现的实际配置差异

检查当前 Block Design 配置后发现：

```text
PCW_EN_TTC0 = 1
PCW_TTC0_PERIPHERAL_ENABLE = 0
```

这说明虽然 TTC0 的外层使能项已被设置，但真正决定 TTC0 外设是否实例化的 `PCW_TTC0_PERIPHERAL_ENABLE` 仍为 0。仅设置前者不足以使新 XSA 包含 TTC 驱动所需的硬件实例。

正确目标状态应为：

```text
PCW_EN_TTC0                 = 1
PCW_TTC0_PERIPHERAL_ENABLE  = 1
PCW_EN_EMIO_TTC0            = 0（推荐）
```

### 7.3 当前最新阻塞点

在 TTC 相关工作推进后，创建 lwIP 模板出现的新错误为：

```text
Invalid Template 'lwip_echo_server' selected for Domain 'standalone_ps7_cortexa9_0'.
lwip_echo_server is not a valid template name for the given BSP.
BSP is missing ['lwip220'].
```

这表明当前阻塞点已经变为 Vitis 软件平台缺少 `lwip220` BSP 库。下一步需要在 Vitis Platform Component 的 `standalone_ps7_cortexa9_0` 域中，通过 BSP Settings / Libraries 添加 `lwip220`，然后重新 Build Platform。

完成前述硬件更新后，还必须重新导出 XSA 并更新 Vitis Platform；否则 Vitis 仍会使用旧 XSA，无法识别 TTC0 或更新后的 GEM0 配置。

## 8. 软件与网络开发建议

建议按两阶段推进，不直接把现有采集服务修改为网络服务。

### 阶段 A：独立验证 Ethernet0 和 lwIP

1. 在 Vivado 确认 TTC0 已真正启用；
2. Generate Output Products；
3. 重新综合、实现、生成 bitstream；
4. 导出新的 XSA；
5. 在 Vitis 更新 Platform 的硬件规格并 Build Platform；
6. 在 BSP 中加入 `lwip220`；
7. 创建独立的 `lwip_echo_server`；
8. 验证 PHY Link、静态 IP 或 DHCP、Ping、TCP Echo 收发。

独立 Echo Server 的价值是将“网口硬件/PHY/协议栈问题”与“采集数据协议问题”分开。只有基础网络收发可靠后，才进入采集服务网络化。

### 阶段 B：采集服务网络化

网络验证通过后，再将采集服务扩展为网络接口。建议初期继续保留 UART 命令行，网络协议优先采用 TCP 控制 + TCP 数据，或 TCP 控制 + UDP 批量数据的组合。初始命令可与现有 UART 语义保持一致：

```text
START <count>
STOP
STATUS
EVENT <index>
SNAP <index>
CLEAR
```

后续还应定义：

- 状态帧格式；
- 事件记录的序号、长度、通道、时间戳和类型字段；
- 快照文件分片/分包格式；
- CRC 或校验机制；
- 网络断开时的归档覆盖策略；
- 上位机确认机制；
- 连续采集时的流量控制和快照下载优先级。

## 11. 本日结论

本日最大的成果是：在不破坏已验证的 DMA、DDR、自动快照和 PS 采集服务的前提下，完成了采集时钟从 PS FCLK 到 PL 独立 50 MHz 时钟源的隔离，并明确了 PS GEM0 直连板载 PHY 的网络架构。系统已从仅能通过 UART 验证的采集原型，进入具备上位机网络通信基础条件的集成阶段。
