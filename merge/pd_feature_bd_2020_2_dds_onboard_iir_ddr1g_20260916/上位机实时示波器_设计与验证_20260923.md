# 上位机实时示波器：设计与验证

> 日期：2026-09-23 ｜ 范围：`sw/host_qt6`（上位机）+ 对 PL/PS 既有代码的读取取证
> 本文只记录**有磁盘证据支撑**的结论。未取证的地方明确标为"未验证"。
>
> **需求在当天经过一次澄清**，定稿工作方式为：**常态充当示波器**（四通道波形 +
> 四通道 360° 相位环同时持续刷新），**需要时才暂停**去读一份完整快照。
> 据此形成的三段式设计见 §3（为什么滚动视图不能算时间轴）、§4.3（常态模式的相位
> 来源与链路仲裁）、§4.4（按需抓快照的编排）。§4.1/§4.2 是通用底座。

## 1. 本次改动解决的四个具体问题

阅读既有 `host_qt6` 代码后确认的缺口，逐条有出处：

| # | 问题 | 证据 |
|---|---|---|
| 1 | **没有缩放/平移**。旧 `PlotWidget` 只重写了 `paintEvent`，没有任何鼠标事件 | 旧 `plot_widget.h` 只有 `setLines/setBars/paintEvent` |
| 2 | **取帧节奏硬编码且脆弱**。在 `scopeFrame` 回调里 `QTimer::singleShot(50, …)` 串下一帧：上限 20 fps、无在途互斥、一次 `ERR` 就永久停摆、无任何统计 | 旧 `main_window.cpp` scopeFrame lambda |
| 3 | **无滚动、无触发**。每帧整体替换画面，没有历史缓冲，也没有触发判定 | 旧 `main_window.cpp` 全文无相关逻辑 |
| 4 | **FFT 是 O(N²) 朴素 DFT 且阻塞 GUI 线程**。512 bin × 1024 点、内层直接调 `cos()/sin()`，单次刷新约 210 万次三角函数调用，且每 10 帧触发一次 | 旧 `main_window.cpp` `updateSpectrum` 分支 |

另外发现一处**数据真实性问题**：旧实现用"每列取一个点"的等间隔抽稀把 520,000 点压到
1500 点绘制。步长 347 点，而 DDS 的 PD 脉冲只有 4 个样点宽 —— 脉冲有极大概率被整根漏掉。
新实现改为 **min/max 包络抽稀**，并在自检里对两种策略做了数值对比（见 §5）。

## 2. 板端协议约束（全部来自磁盘代码，非推测）

| 约束 | 值 | 出处 |
|---|---|---|
| 服务端口 | TCP 6001 | `ps_service/TCP_API_v10_冻结说明.md` |
| `SCOPE ON [samples]` | `samples ∈ [256,2048]` 且为 4 的倍数，默认 1024 | `tcp/pd_tcp_service.c` `PD_SCOPE_DEFAULT_SAMPLES/MAX_SAMPLES`、`start_scope()` |
| 每个采样时刻字节数 | 6（四通道 12-bit offset-binary） | `include/pd_snapshot_unpack.h` `PD_SNAPSHOT_BYTES_PER_SAMPLE` |
| 帧头 | `SCOPE V1 seq= samples= bytes= fs=26000000 crc32=` | `pd_tcp_service.c` `start_scope_frame()` |
| 二进制负载长度 | `bytes = samples × 6`（1024 点 → 6144 B） | 同上 |
| 帧内容位置 | DDR 环上 `(wr_ptr + size - 24576 - bytes)` 起，24 字节对齐 | 同上，`PD_SCOPE_SAFETY_BYTES` |
| 前置条件 | 必须处于采集运行态（`state != 0`），否则 `ERR SCOPE requires a running acquisition` | `pd_tcp_service.c:1034` |
| 并发限制 | 一次只能有一个传输在途，第二个 `NEXT` 回 `ERR SCOPE transfer is still active` | `pd_tcp_service.c:1039` |
| 采样率来源 | **帧头里写死 `fs=26000000`** | `pd_tcp_service.c` `start_scope_frame()` |
| **`GET EVENT` 在采集中允许** | 运行态可读，板端注释写明"for live PRPD display" | `pd_tcp_service.c` `start_get()` 顶部注释与状态判断 |
| **`GET SNAP` 强制 IDLE** | 运行态回 `ERR GET SNAP requires idle while acquisition is running` | 同上 |
| PRPD 查询 | `PRPD ...` 要求服务 IDLE | `TCP_API_v11_PRPD说明.md` |
| 事件包位域 | `type=word>>56`；Q8.8 有符号 `(word>>40)&0xFFFF`；峰值包 `channel=(word>>25)&0x3` | `ps_service/src/pd_event_decode.c` |

上位机严格遵守上述全部约束：`ScopeStream::setSamples()` 在本地就把非法值夹到
`[256,2048]` 且 4 的倍数；`m_frameInFlight` 保证不并发；帧长不满足 24 字节块整数倍时
拒绝使用（与 PL 只以 24 字节块写 DDR 的事实一致）。

## 3. 关键结论：SCOPE 帧之间**不是**连续时间

这是本次设计最重要的判断，直接决定"实时滚动"能不能画成连续波形。

### 3.1 定量分析

| 量 | 值 | 来源 |
|---|---|---|
| DDR 环大小 | `0x07FF_E000` = 134,209,536 B ≈ 128 MiB | `pd_ddr_defines.vh:81` |
| 环起始 | `0x1000_2000` | `pd_ddr_defines.vh:80` |
| 窗口距写指针 | 24,576 B（24 KiB） | `PD_SCOPE_SAFETY_BYTES` |
| 单帧窗口长度 | 1024 × 6 = 6144 B | 计算 |
| 写指针推进速率 | 26 MSPS × 6 B = **156 MB/s** | 采样率 × 每样点字节数 |
| 环回绕一圈 | 134,209,536 / 156e6 ≈ **0.86 s** | 计算 |

两次 `SCOPE NEXT` 之间的往返时间（TCP + PS 的 `Xil_DCacheInvalidateRange` + `memcpy` +
回传 6144 B）保守取 **1 ms**，则写指针已前进约 156 KB：

```
帧间隔内前进 / 窗口长度 = 156,000 / 6,144 ≈ 25 倍
时间覆盖率 = 6,144 / (6,144 + 156,000) ≈ 3.8%
```

即使按 100 µs 的乐观往返估算，前进 15.6 KB 仍是窗口的 2.5 倍，覆盖率也只有 28%。

**结论：连续两帧在真实时间轴上相隔约 25 个窗口宽度；滚动视图只能覆盖经过时间的
百分之几。把它画成一条连续曲线，等于伪造时间轴。**

### 3.2 据此确定的设计

1. **滚动模式下横轴改为"到达样本序号"**，界面左下角与图例中明确拼写
   "帧间不连续，此轴不代表时间"；CSV 导出的文件头也写入同样的警告。
2. 提供**触发模式**作为"稳定观察"的替代路径：帧内判定 + 无触发帧保持上一幅，
   并可把触发点固定到视图的预触发比例位置（对齐显示）。
3. 提供**归档记录波形**页签：完整快照 3,120,000 B = 520,000 点 = **恰好一个工频周期
   的连续 20 ms 数据**，横轴完全可信，可缩放浏览、加游标、导出。
   ——需要"真正的时间轴"时用这个，而不是滚动视图。

### 3.3 各视图的能力边界

| 视图 | 长度 | 横轴可信度 | 时间分辨率 | 适合回答的问题 |
|---|---|---|---|---|
| 实时（单帧） | 256..2048 点 = 9.8..78.8 µs | 帧内可信 | 38.46 ns | 波形形态对不对？触发电平设哪？ |
| 触发 | 同上 | 帧内可信 | 38.46 ns | 周期事件稳不稳？脉冲形状一致吗？ |
| 滚动 | 默认 32768 点（可设） | **不可信** | — | 事件密度趋势、偶发异常的外观 |
| 归档记录 | 520,000 点 = 20 ms | **完全可信** | 38.46 ns | 完整工频周期内的相对时序、游标测量 |

## 4. 模块划分

新增（全部在 `sw/host_qt6/`）：

| 文件 | 职责 |
|---|---|
| `pd_sample_codec.{h,cpp}` | 6 字节采样契约的唯一解析点：解码、24 字节块校验、min/max/mean、触发查找 |
| `fft_engine.{h,cpp}` | 预计算旋转因子的迭代 radix-2 FFT；去直流 + 周期 Hann + 相干增益校正 |
| `scope_widget.{h,cpp}` | 示波器绘图控件：缩放/平移/游标/触发标记/包络抽稀/滚动缓冲 |

| `selftest.cpp` | 离线自检（独立控制台程序，失败返回非零） |

改动：

- `pd_tcp_client.{h,cpp}`：SCOPE 帧不再计入下载进度条（原来会让进度条每帧乱跳）。
- `main_window.{h,cpp}`：新增"实时示波器"页签与完整控制面板；取帧期间暂停 PRPD 轮询、
  禁用归档下载；CSV/PNG 导出。
- `CMakeLists.txt`：拆成 `pd_host_core` 静态库 + GUI 可执行 + 自检可执行，保证两边共用
  同一份解析实现，避免口径发散。

### 4.1 取帧状态机

```
Idle ──start()──> WaitingAcquisition ──STATUS state!=0──> Enabling ──OK SCOPE ON──> Streaming
                        ↑                                                             │
                        └────────── ERR requires running acquisition（自动 START 0）────┘
Streaming ──singleShot 完成──> Paused
Streaming ──连续 3 次帧超时 / 无法自动处置的 ERR──> Fault（停止并把处置权交回用户）
```

关键实现点：

- **帧节奏**：默认 20 ms 最小间隔，给 PS 留出处理 DMA 与归档的时间（可设 0..1000 ms）。
- **在途互斥**：`m_frameInFlight`，杜绝 `ERR SCOPE transfer is still active`。
- **看门狗**：单帧 3 s 未到 → 计数 + 重试；连续 3 次 → 进入故障态。**不静默重试掩盖故障**。
- **停止时的 SCOPE OFF**：若帧在途，置 `m_scopeOffPending`，等帧收完再发
  （二进制传输期间客户端会拒发文本命令）。
- **seq 跳号**：`SCOPE V1 seq=` 每帧自增 1，差值 > 1 计一次跳号。
  重启取帧时重置基线，避免把重启误报成跳号。

### 4.2 FFT 口径（与 PS 侧对齐，可互校）

PS 侧 `pd_spectrum.c` 的幅值计算是"每级 `>>1` 缩放后取 `isqrt(power) * 4`"。对幅度 A 的
单音，其自检用例（A=1024）期望 `amplitude_code ∈ [900,1150]`，反算即
`amplitude_code ≈ A`。上位机采用同一口径：

```
A = 2·|X[k]| / (N · coherentGain)        coherentGain = 0.5（周期 Hann）
```

自检实测：输入幅度 1024 码的单音 → 输出 **1024.0 码**，与板端 `amplitude_code` 数值一致。
因此可以把上位机的 FFT 峰值与板端 `SPECTRUM AUTO SNAP n` 的输出直接对照。

### 4.3 常态示波器模式：波形与相位环并行刷新

需求是"常态当示波器：360° 参考相位环 + 四通道波形一直持续更新"。这里的关键是
**相位从哪来**。

复核板端代码后确认：**只有 PL 的 12-bit 相位字段是权威相位来源**，它在 64-bit 特征
事件包里（峰值包 bits 39:28）。板端 `pd_event_decode.c` 只取 type/Q/channel，
**没有取相位字段**——也就是说相位字段的位移与位宽在上位机里是唯一定义点。

可选的相位获取路径只有两条，其中一条被板端明确支持：

| 路径 | 可行性 | 依据 |
|---|---|---|
| `GET EVENT` 读事件包 | ✅ 运行态允许 | `start_get()` 注释"for live PRPD display" |
| `GET SNAP` 读快照后自行算相位 | ❌ 运行态被拒，且快照里没有 sync | `start_get()` 的 IDLE 门禁；DDR 只存 6 字节通道数据 |
| 上位机用墙钟推算 50 Hz 相位 | ❌ 帧间间隙不可观测（§3），误差无法界定 | 本报告 §3 的定量分析 |

因此设计为：**波形走 SCOPE（持续），相位环走 EVENT（在取帧间隙插入小回合）**。
这不是"一直在下载快照"，而是每 500 ms 读一次体积很小的归档事件包。

**链路仲裁**（板端同一时刻只允许一个二进制传输）：

```
每 500 ms 触发一个 PRPD 回合
  1. ScopeStream::setSuspendRequests(true)   ← 不再发起新的 SCOPE NEXT
  2. 等 ScopeStream::inFlightChanged(false)  ← 在途帧收完，链路空闲
  3. CATALOG → EVENT SEQ n → GET EVENT SEQ n 0 bytes
  4. 回合结束 → setSuspendRequests(false)    ← 立刻恢复取帧
```

- 回合总超时 5 s，任何一步回复丢失都不会让链路被永久占住。
- 事件序号若已被环形覆盖，只跳过该条并明确记一条日志，**不清空已有画面**。
- 事件包 type 既非 0（峰值）也非 1（周期）时计为"格式不认识"并报错，
  不把不认识的包当数据画到环上。

**相位环的呈现**：加入时间老化（默认只保留最近 10 s 的点，按新近程度决定亮度，
最新点白色描边）。这样环表现为"持续刷新"，而不是无限堆积、越画越糊的点云。

### 4.4 按需模式：暂停抓快照

`GET SNAP` 的 IDLE 门禁决定了两件事：一是抓快照必须真的暂停采集，二是抓完之后
板端本来就处于 IDLE，可以顺手跑 `ANALYZE` / `FFT SNAP` / `PRPD BINS`。
上位机把这条链编排成一个按钮：

```
暂停并抓取快照
  STOP → 轮询 STATUS 直到 state=0
       → CATALOG 取 snap_seq=[first,next)，选 next-1（最新一份）
       → SNAP SEQ n 取元数据 → GET SNAP SEQ n offset 16384 循环，逐段 CRC32 校验
       → 载入「归档记录波形」（520,000 点 = 20 ms 连续，横轴可信）
恢复取帧
  → 自动 START 0 + SCOPE ON
```

每阶段 10 s 超时；下载阶段按"有无分段进展"判定（每收到一段刷新计时），
超时明确报错退出，不无限等待。

**避开的一个坑**：`m_stream->stop()` 会**同步**发出 `stateChanged`，那里会按"非取帧"
重新使能归档下载控件。因此必须先置好编排阶段标志、先锁住归档控件，再停取帧；
否则下载期间用户可以点"下载本段"，造成两个二进制传输互撞。

## 5. 离线自检结果（无板端，60 项全通过）

运行：`build/…/pd_host_selftest.exe` → 通过 60 项，失败 0 项，退出码 0。

### 最有价值的一项：三方交叉印证

主机侧用 RTL 的 `tri_wave` / `pd_pulse` 公式重建 520,000 点，再按 `pd_pack48` 规则打包、
经上位机解码函数还原后统计最小值：

| 通道 | 基线 | 三角幅度 | 主机重建最小值 | **板上实测最小值** | 一致 |
|---|---:|---|---:|---:|---|
| CH0 | 2048 | `>>>2` → ±16 | 2032 | **2032** | ✅ |
| CH1 | 2056 | `>>>2` → ±16 | 2040 | **2040** | ✅ |
| CH2 | 2038 | `>>>1` → ±32 | 2006 | **2006** | ✅ |
| CH3 | 2062 | `>>>2` → ±16 | 2046 | **2046** | ✅ |

四个值精确相等，说明 **"RTL → pd_pack48/pd_pack192 打包 → DDR → 上位机解码"** 这一整条
链的理解是正确的，而不是看起来差不多。

### 其余各项

- **采样契约**：0x000/0xFFF/0x800/交叉位模式往返编码解码逐位一致；7 字节输入被拒绝；
  24 字节 → 4 个采样时刻、间隔 = 1/26 MHz。
- **DDS 真值**：整段 3,120,000 字节解出 520,000 点；四通道脉冲四样点增量为
  **720 / 600 / 460 / 300** 码（与 RTL 常量一致）；四通道最大值 2769/2772/2743/2796，
  距 4095 均有余量（未饱和）；CH1 在 256 个采样点内遍历全部 256 个相位值。
- **FFT**：单音 bin 37 → 命中 bin 37、幅度 1024.0 码、去直流估计 2048.000、频率
  939,453.125 Hz（= 37 × 26 MHz / 1024）；叠加 300 码直流后仍命中 bin 37；
  矩形窗与 Hann 窗主峰位置一致；样本不足 1024 点时**返回空结果而不是零填充**。
- **性能**：同一 Debug 构建下，4 通道 1024 点 FFT = **5.9 ms/帧**，
  原朴素 DFT = **164 ms/帧**，**加速 27.8 倍**（Release 构建会进一步下降）。
- **触发**：上升沿命中下标 100；下降沿同信号返回 -1；含阈值抖动信号在有迟滞时仍锁定
  下标 100；全程未越阈值时返回 -1（不误触发）。
- **抽稀策略**：同一份 520,000 点、脉冲在 65003 的数据压到 1000 列 ——
  min/max 包络峰值 **2768 码**（脉冲保留），等间隔抽样峰值仅 **2048 码**（脉冲丢失）。
- **板端回复解析（14 项）**：新增 `pd_reply_parse.{h,cpp}` 把 CATALOG / EVENT 元数据 /
  SNAP 元数据 / STATUS / SCOPE V1 / DATA V2 / PRPD_BINS 的解析集中成唯一实现，
  并用**上板实抓日志原文**作测试向量。含反向用例：缺 `snap_seq`、缺 `peaks/cycles`、
  `values` 个数与 `count` 不符时都必须判**解析失败**，不得拿默认值当数据。
- **事件包位域（相位环的数据源）**：按 `pd_event_decode.c` 的字段位置正向构造事件字，
  再交上位机解码，5 组用例（含 Q8.8 负值、相位 0/90/180/270/近 360°）全部逐位吻合；
  周期包被识别为"正常跳过"（`valid` 保持 true）；未知 type 使 `valid=false`
  ——**不把不认识的包当数据用**。

## 6. 上板验证判据

### 6.1 前置

- 板端 ELF 必须是含 `SCOPE` 命令的 PS 服务（`CONFIG` 回复含 `scope=<当前>/<上限>` 字段）。
- 电脑网卡与板端同网段，`TCP 6001` 可达。

### 6.2 通过条件

| # | 判据 | 期望值 | 不通过说明什么 |
|---|---|---|---|
| 1 | 连接后欢迎行 | `PD_ACQ TCP PS-2 READY` | 服务未运行或端口不对 |
| 2 | `CONFIG` | 含 `scope=` 字段 | 板端 ELF 版本过旧，无 SCOPE 命令 |
| 3 | 点"开始取帧" | 自动 `START 0` → `SCOPE ON 1024` → 状态变"取帧中" | 自动编排逻辑异常 |
| 4 | 统计行帧率 | 稳定非零（默认最小间隔 20 ms 时上限约 50 fps） | 链路慢或帧间隔设置过大 |
| 5 | `CRC 失败` | **0** | 链路或解析有问题，**必须查明，不得忽略** |
| 6 | `协议错误` | **0** | 命令序列与板端状态机不匹配 |
| 7 | `超时` | 0（或启动瞬态后归零并保持） | PS 侧被其他任务占用 |
| 8 | 时基 256 / 512 / 1024 / 2048 | 均可取到帧，横轴单位随之变化（9.85/19.7/39.4/78.8 µs） | 板端 samples 校验或上位机换算有误 |
| 9 | 触发模式（CH0、上升、电平 2400） | 只在含脉冲的帧刷新；`触发未命中` 持续上升 | 触发判定或电平设置问题 |

## 7. 需要反馈给板端/协作方的四处

1. **`fs` 写死 26 MHz**。`pd_tcp_service.c` 的 `start_scope_frame()` 把
   `fs=26000000` 写进帧头。将来切 65 MSPS 时必须同步改这一处，否则上位机时间轴错 2.5 倍。
   建议改为读取运行时 FFT 采样率配置（`SET FFTFS` 已经维护了同类信息）。
2. **API 版本号不一致**。`CONFIG` 回 `api=12`（`pd_tcp_service.c:176`），
   `REPORT` 回 `api=11`（同文件 `:205`），而 `TCP_API_v11_PRPD说明.md` 写的是 `api=11`。
   上位机目前不对版本号做硬门禁（只检查 `scope=` 字段是否存在），但文档与实现应当统一。
3. **`SCOPE` 若将来要支持真正连续的滚动显示**，需要板端在帧头里带上 `ring_wr_ptr`，
   或提供"从某偏移连续读 N 字节"的命令。当前协议下上位机无法观测帧间数据间隙，
   只能如实标注为不连续。
4. **相位字段在上位机里是唯一定义点**。`pd_event_decode.c` 只取 type/Q/channel，
   没有取相位（bits 39:28，12 位），所以 PL 若改相位位宽，上位机不会自动跟着错，
   而是**静默画到错误的相位上**。上位机已把该位域提成 `pd_sample_codec.h` 的
   `eventpacket` 具名常量并加了自检断言；建议板端 `EVENT DETAIL` 之外再提供一个
   显式的相位字段宽度回报（类似 `CONFIG` 里的 `prpd_bins=`），让两端能互校。

## 8. 一处需要更正的既有记录

项目长期记忆里写着"DDS 三角频率 = 304.7/507.8/710.9/1117.2 kHz（不是 101.5625 kHz）"。
按 RTL 复核，**这个更正是错的**：`pd_dds_adc_source.v` 的 `tri_wave()` 是 8-bit 相位的
三角映射（`phase[7]` 决定升降），相位步进 3/5/7/11 与 256 均互素，因此四通道的三角波
周期**都是 256 个采样点**：

```
f_triangle = 26 MHz / 256 = 101.5625 kHz（四通道相同，差别只在初相与直流基线）
```

304.7/507.8/710.9/1117.2 kHz 恰好是 `101.5625 × {3,5,7,11}`，即把"相位步进"误乘了基频。
反证：三角幅度 ±16/±32 对应的四通道最小值 2032/2040/2006/2046 只有在 256 点周期下才成立，
而这四个值与此前板上实测完全一致。

## 10. 上板实抓日志复盘（2026-09-23 13:08，真实板端）

这次拿到了上板运行的完整 TCP 日志与界面截图，逐条核对后确认了三类问题：
两个是**上位机缺陷**（已修），一个是**板端配置现象**（需板端处置）。

### 10.1 量化事实

| 观测 | 数值 | 出处 |
|---|---|---|
| 连续两次 CATALOG 之间 `event_seq` 前进量 | 中位数 **101** | 日志中 31 个 CATALOG 窗口 |
| 事件归档槽数 | **16** | `CATALOG … slots=16` |
| ⇒ 一条记录的存活时间 | ≈ 回合间隔的 **16%**（回合 500 ms → **约 79 ms**） | 计算 |
| 每回合硬试 4 条的实际命中 | **1–2 条** | 逐回合统计（如 `[20711,20727)`：20723✓ 20724✓ 20725✗ 20726✗） |
| 事件记录的两种形态 | `bytes=8224 peaks=1027 cycles=1` 与 `bytes=8 peaks=0 cycles=1` | 日志 |
| 相位环落点分布（截图） | CH0 **14** 点 / CH1 **14** 点 / CH2 **14336** 点 / CH3 **2** 点 | 界面截图 |
| 取帧状态（截图） | `状态：空闲`、`帧率 0.0 fps`、`已画帧 0` | 界面截图 |

`14336 = 14 × 1024`：即 14 条记录、每条贡献 1024 个 CH2 峰值字，几乎全部落在 CH2。

### 10.2 缺陷一：回合策略与归档寿命不匹配（上位机）

原实现每回合固定从 `[next-4, next)` 取 4 条。但记录只活约 79 ms，所以**后两条几乎必然失效**，
日志里表现为大量 `ERR … sequence is outside the retained archive window`。
一半以上往返是注定失败的浪费。

**修法**：候选改为"最新优先 + 每回合只求一条含峰值的记录"，
并且一遇失败立刻收手（不补试）；单条 8224 字节记录已含约 1027 个峰值字，
足够填满相位环。

### 10.3 缺陷二：归档冻结时无限空转 + 链路标志卡死（上位机）

日志尾部在 `STOP` 之后出现**连续 30 多次 `>> CATALOG`**，内容一模一样
（`event_seq=[20900,20916) state=0`）——采集已停、归档冻结，回合却按间隔一直空发，
把日志刷满毫无收益。更严重的是：`m_eventDownloadInFlight` 若因某次回复丢失而未清，
会让**后续"暂停抓快照"的编排被永久挡住**（`pumpSnapshotGrab` 一直早退），
表现就是"点了暂停抓取没反应、没数据"。

**修法**：
1. 连续两次 CATALOG 窗口不变 → 判定归档冻结，退避 3 s 并把状态写进界面；
2. 回合超时分支里**显式清掉在途标志**，使链路状态自愈；
3. `pumpSnapshotGrab` 改为"链路被占用时推迟阶段计时"，不再把"等链路"误判成"阶段超时"。

### 10.4 缺陷三：相位直方图要 IDLE，而取帧意味着 RUNNING（上位机）

原来点"读取 64 桶"时若在取帧，只回一句"请先暂停"——用户点几次都拿不到数据
（截图里的"相位直方图无数据"）。

**修法**：改成自动代跑流程——停取帧 → `STOP` → 轮询 `STATUS` 到 `state=0` → 自动发
8 次 `PRPD BINS`，并提示"点恢复取帧回到示波器模式"。
同一个暂停状态机用 `PauseReason{Snapshot,Bins}` 区分到达 IDLE 后的动作。

### 10.5 缺陷四：连接后不自动取帧（上位机）

截图显示 `已画帧 0`、左侧仍是"等待数据"占位——**用户连上了，但波形从未开始**
（需要手点"开始取帧"，且 SCOPE 还要求板端 RUNNING）。
这与"其余时刻上位机充当示波器、一直持续更新"的诉求直接冲突。

**修法**：新增「连接后自动取帧」勾选框（默认勾选，可取消）。勾选时连接后自动走
`STATUS →（必要时 START 0）→ SCOPE ON → 持续取帧`，并在日志里写明它实际发了什么，
不做无提示的板端状态变更。

### 10.6 板端现象：事件几乎全部来自 CH2（需板端处置）

这是本次最有价值的发现，有**代码级根因**：

- `pd_axil_regs.v:359` 的上电默认门限是 **`r_thresh[c] <= 32'd40`（40 ADC 码）**；
- `pd_feature_core.v:502` 的判决是幅值比较 `gate = (amp >= cfg_thresh)`；
- DDS 各通道相对 2048 的偏离幅度：

| 通道 | 基线 | 三角幅度 | 相对 2048 的最大偏离 | 能否越过 40 码门限 |
|---|---:|---|---:|---|
| CH0 | 2048 | `>>>2` → ±16 | 16 | ❌ |
| CH1 | 2056 | `>>>2` → ±16 | **24**（2056-2048=8 的直流偏置 + 16） | ❌ |
| CH2 | 2038 | `>>>1` → ±32 | **42**（10 的直流偏置 + 32） | ✅ |
| CH3 | 2062 | `>>>2` → ±16 | **30** | ❌ |

**只有 CH2 能越过 40 码门限**——这与截图里 CH2 有 14336 点、其余三个几乎为零**完全吻合**。

含义：当前相位环上画的不是局放脉冲，而是 **DDS 背景三角波在 CH2 上反复越过门限**
产生的密集"事件"（也解释了 202 条记录/秒、归档 79 ms 就轮转一圈的高速率）。

**建议（板端）**：把门限从默认 40 提到能盖过 DDS 背景、但低于 PD 脉冲增量的水平。
PD 脉冲增量是 **+720/+600/+460/+300 码**，而最大背景偏离是 42 码，
因此门限取 **100~200 码** 即可让每个 20 ms 工频周期每通道只出现 1 次峰值事件
（CH0≈45°、CH1≈135°、CH2≈225°、CH3≈315°），相位环才会呈现真正的局放脉冲分布。
门限可通过 AXI-Lite `THRESH`（偏移 `0x0C`，按通道）写入，无需重综合。

### 10.7 顺带确认的一件事

日志里 `GET EVENT` 在 `state=1`（采集中）时被板端正常接受并返回数据，
与 §4.3 引用的板端注释一致——**常态示波器模式下读事件归档的架构是成立的**，
不需要暂停采集。

## 11. 第二次上板复盘（2026-09-23 13:21）：SCOPE 命令缺失与布局问题

### 11.1 ⛔ 波形出不来的真正原因：板端 ELF 没有 SCOPE 命令

日志证据（同一条命令两次独立复现）：

```text
[scope] 采集运行中，发送 SCOPE ON 1024。
<< STATUS state=1 packets=440 events=21356 ...          ← 采集确实在跑
<< ERR unknown command; type HELP                        ← SCOPE ON 被拒
...
>> STOP
<< ERR unknown command; type HELP                        ← 停取帧时发的 SCOPE OFF 也被拒
<< OK stop requested                                     ← STOP 本身是认识的
```

⇒ **当前烧写的 ELF 里没有 `SCOPE` 命令**（`STOP`/`STATUS`/`CATALOG`/`EVENT`/`GET`/`SNAP`
都正常，只有 SCOPE 系列回 unknown）。所以 `SCOPE V1` 帧永远不会到达，波形永远空着。
处置：用当前 `sw/ps_service/` 重新编译并下载 ELF。

**这个错误此前被上位机静默吞掉了。** `handleBoardError` 只匹配已知错误字符串
（`still active` / `SCOPE is off` / `requires a running acquisition` / `ring is not ready`），
`ERR unknown command` 不匹配任何一条，且当时状态是 `Enabling` 而非 `Streaming`，
连 `catchAll` 也不成立 → 直接 `return`，什么都不报。结果就是"界面没数据但也没有报错"。

**修法（两条）**：

1. **固件能力探测**：`start()` 先发 `CONFIG`，用回复里有没有 `scope=` 字段判定能力；
   没有就进故障态并明确提示更新 ELF。新增 `pdreply::parseConfig`，
   自检含正向与反向（旧固件无 scope 字段）两个用例。
2. **错误不再被吞**：在 `Enabling` / `CheckingFirmware` 状态下收到**任何** `ERR`
   一律判故障并报出原文。这两条是"等 SCOPE ON 的 OK"期间唯一可能的回复来源，
   没有理由继续匹配字符串。

### 11.2 快照抓取被误判超时（上位机自身缺陷）

日志里 3,120,000 字节的快照**明明在正常分段推进**，却在第 38 段被中止：

```text
<< DATA V2 kind=SNAP index=3 offset=622592 bytes=16384 crc32=14361a2e
ERR 快照抓取中止：下载已 10000 ms 无进展      ← 误判
<< DATA V2 kind=SNAP index=3 offset=638976 bytes=16384 crc32=88f9cdd6   ← 还在下
...
OK 下载完成：… 3120000 字节，每段 CRC32 已校验   ← 其实成功了
```

根因：`pumpSnapshotGrab()` 的 `Downloading` 分支**无条件调用 abort**，理由写的是
"走到这里说明已超时"——但真正的超时判定在最上面的 elapsed 检查里，
而那个检查会被 `downloadProgress` 正常刷新。于是分支一到就杀，与超时无关。

**修法**：`Downloading` 分支改为不做任何事（`break`），超时只由顶部 elapsed 检查决定。

### 11.3 界面在 1280×720 级别屏上放不下（上位机自身缺陷）

用户截图显示：相位环被切掉、日志被挤出可视区、控制区中间有一条白带。

用新增的 `--screenshot WxH` 离屏渲染实测，**请求 1280×720 与 1320×780 都渲染成
1550×869** —— 说明窗口的**最小尺寸就是 1550×869**，Qt 拒绝再缩小。
根因是控制区的 11 列网格 + 相位环工具栏长条把最小宽度撑到了 1550。

修法：

| 项 | 改动 |
|---|---|
| 控制区 / 相位环工具栏 | 包进 `QScrollArea`（`setMaximumHeight` 196 / 78），不再参与撑宽窗口 |
| 主区 | 改为纵向 `QSplitter`（页签视图与日志），高度由用户拖动分配 |
| 采集/归档/手动三个命令框 | 移入独立页签「命令与归档」，从主纵向布局里移除约 150 px |
| 全局底色 | 加 `QWidget { background:#101722 }`：此前子控件回落到系统浅色主题，中间那条白带就是这么来的 |
| 最小尺寸 | 波形控件 160 高、环形面板 240×130、日志 60 高 |

改后实测最小可到 **1024×700**。

**顺带产物**：`pd_acquisition_desktop --screenshot <路径> [WxH]` ——
离屏渲染一张界面截图再退出。布局问题（控件被切、日志被挤出）光看代码判断不了，
必须看图；有了这个开关就能在改动后立刻核对任意分辨率。

### 11.4 仍待确认的一件事

本次日志里相位环落点与上一轮不同：上一轮 **CH2 = 14336 点**（其余 14/14/2），
本轮 **CH3 = 8192 点**（其余各 8 点），且都是 `1024 × 记录数` 的整倍数，

### 12.2 椭圆图谱的几何模型（由参考图反推并验证）

参考图一里最显眼的特征是：**竖线中间长、两端短，且关于椭圆水平轴上下对称**。
这不是画法偶然，而是椭圆参数化的必然结果。把椭圆当**工频相位刻度盘**：

```
x(θ) = cx + Rx · sin θ
y(θ) = cy − Ry · cos θ          （θ = 0 在正上方，顺时针增加）
```

于是一个发生在相位 θ 的脉冲，在 x(θ) 处画竖直对称线。该 x 处椭圆的上下边界是
`cy ± Ry·|cos θ|`，而 **|cos θ| 在 θ=0/180（x 恰在中轴）处为 1、在 θ=90/270（椭圆两端）处为 0**
—— 正好解释"中间长、两端短"。这个模型与参考图逐点吻合，因此采用它而不是径向辐条
（径向辐条仍作为可选项保留，相位指向更直观）。

**相位对应关系**另外用三样东西显式表达，而不是只靠形状让人猜：

- 椭圆上每 30° 一个径向短刻度；
- 四个象限标 `0° / 90° / 180° / 270°`；
- 选中某个脉冲时，从圆心到该相位点画一条径向线 + 白色圆点，直接指出"它在这个相位"。

**缩放**：滚轮以鼠标为锚点缩放（`c' = p − (p − c)·f`，保证鼠标下的点不动）、
`Ctrl+滚轮` 只缩放幅度轴、左键拖拽平移、双击复位，右上角常显 `图谱 ×N ｜ 幅度 ×N`。
参考图二那种"椭圆带被放大成密集噪声带"就是缩放后的形态。

**配色照参考图**：CH1 黄 / CH2 青 / CH3 红 / CH4 品红；头部信息条也是照参考图
（通道徽章 + 幅值 + 频带标签），左下角三个小按钮（复位 / 适配 / 显隐）做成可点区域。

### 12.3 ⭐ 关键取证：事件包幅度字段的单位

这一条决定了椭圆图的纵轴能不能诚实标注，也决定了"波形脉冲"与"图谱事件"能否互相印证。

| 项 | 结论 | 依据 |
|---|---|---|
| 幅度字段定义 | `[55:40]` 16-bit **有符号 Q8.8 视在电荷量** | `pd_feature_core.v:554` |
| 板端算法 | `q_field = sat16(q_signed_codes × SCALE_q88) >>> 8` | `pd_feature_core.v:375,390,435` |
| SCALE 上电默认 | **`32'd256`（Q8.8 = 1.0）** | `pd_axil_regs.v:360` |
| ⇒ 默认标定下 | **`q_field` 的数值就是该脉冲的 AD 码幅度** | 代入上式即得（×256 后 >>>8，精确可逆） |
| ⇒ pC 读数 | `pC = q_field / 256`，但**这不是真实标定**，只是占位 | SCALE=1.0 意味着 1 AD 码 = 1/256 pC |
| 相位字段 | `[39:28]` 12 位（`PD_PH_FIELD_W=12`） | `pd_defines.vh:36` |
| 极性 | `[27]`，0=负 1=正 | `pd_feature_core.v:556` |
| evt_seq | `[24:0]` 25 位，每通道自增 | `pd_feature_core.v:549-550` |

**两条由此而来的实际收益**：

1. **波形脉冲与图谱事件可以按幅值互相印证**——因为默认标定下两者的数值域相同
   （事件 q 的原始值 = 该脉冲的 AD 码幅度）。这是 §12.6 联动的基础。
2. **`evt_seq` 以前完全没用上**。它是每通道自增序号，在**同一条记录内**应当连号；
   不连号说明 PL→PS→归档这条链丢了事件。上位机已加入该统计（跨记录比较无意义，
   因为上位机是刻意跳着取记录的）。

**同时发现一处 RTL 注释自相矛盾**（已上报）：`pd_feature_core.v` 的位域说明块
（:555-557）写 `[39:30] phase / [29] polarity / [28:27] ch_id`，那是 **PH_FIELD_W = 10**
的布局；而同文件 :575-576 写"峰值包 ch_id 在 `[26:25]`"，与 PH_FIELD_W = 12 的实际拼接一致。
当前配置是 12，故以 `[26:25]` 为准。上位机把三个位移改成**由 `kPhaseBits` 推导**
（`40−kPhaseBits` / `39−kPhaseBits` / `37−kPhaseBits`），并把 RTL 的位位置**硬写进自检**，
这样板端改位宽时是一行改动、且必然被测出来。

### 12.4 卡死热点：定位到代码行与量级

四类热点，全部在 GUI 线程里做重活。下面每条都给出位置与量级，不是"感觉卡"。

| 编号 | 位置 | 每次重绘/触发做的事 | 量级 |
|---|---|---|---|
| H1 | `PrpdPanel::paintEvent` + `peakAmplitude()` | ①遍历全部点求峰值 ②主循环里对**每个点**调 `cos`、`sin`、构造一个 `QPen`、再 `drawPoint` | 2 万点 ×(2 次三角函数 + 画笔构造 + 逐点绘制) |
| H2 | `ScopeWidget::drawTraces` | 每次重绘对可见区间做 min/max 包络抽稀 | 520,000 点 ×4 通道 = **208 万次比较**，而拖拽/游标/实时刷新都会重绘 |
| H3 | `loadSnapshotPlots`（GUI 线程） | 读 3.12 MB 文件 → `decodeFrame` 解 200 万个 double → `measure` 再遍历 200 万点 → 4 次 FFT | 一次阻塞数百毫秒，期间界面完全无响应 |
| H4 | 日志 `appendPlainText` | SCOPE 帧 20 ms 一条、快照下载 190 条 DATA 头，逐条追加都要重排文本 | 持续争抢 GUI 线程 |
| H5 | `PrpdPanel::setStatusText` | 内部 `update()`，而一次数据到达会对 4 个面板各调一次 | 一次数据触发 4 次重绘 |

其中 **H3 是"暂停抓取之后卡死"的直接原因**：快照下载完成后紧接着在事件循环里
解 200 万个点并算统计，界面在这几百毫秒里不响应任何输入。

### 12.5 多线程架构与渲染瘦身

```
GUI 线程（只做绘制与交互）
  ├─ 渲染节流：30 ms 内的多次 update() 合并成一次重绘
  ├─ 日志合并：120 ms 合并追加一次 appendPlainText（上限 2000 条，超出只计数不排队）
  └─ 控件只读"已准备好的绘制数据"

PdAnalysisWorker（常驻工作线程，QThread）
  ├─ decodeSnapshotFile / decodeSampleBlock  → 解包 + 统计 + 脉冲检测 + FFT
  ├─ decodeEventFile / decodeEventBatch      → 事件包解码
  ├─ computeSpectrum / detectFramePulses
  └─ writeFile                               → 大文件 IO
     结果经 queued 信号回传；波形帧用 QSharedPointer 传递（引用计数，零拷贝）
```

**为什么不把 TCP 套接字也搬走**：`QTcpSocket` 是异步的，本身不阻塞事件循环；
真正的开销在解码与统计（H3）。把它们搬走即可达到目的，而套接字留在 GUI 线程
可以让所有命令调用保持同步、改动面小得多。这是明确取舍，不是遗漏。

**实时帧为什么留在 GUI 线程**：一帧只有 1024 点，脉冲检测是 O(N) 直方图统计
（约万次整数运算），跨线程往返的成本高于计算本身。只有 520,000 点的静态记录
才交给工作线程。判据按数据规模分流，而不是一律跨线程。

**渲染瘦身**：

| 改动 | 效果 |
|---|---|
| `ScopeWidget` 包络抽稀结果按 (数据版本, 视图范围, 像素列数) 缓存 | 重绘成本从 O(样本数) 降到 O(像素列数)，约 500× |
| 相位→sin/cos 改 4096 项查表（与 12-bit 相位窗号一一对应） | 热循环内**没有三角函数调用** |
| `PrpdPanel` 背景点改 (相位桶 × 幅值桶) 密度网格，只遍历非空格子 | 去掉逐点 `drawPoint` |
| `PrpdPanel` 峰值 / 最新点 / 高亮点在数据入口算好缓存 | paint 里没有 O(N) 循环 |
| `EllipsePanel` 背景点进密度网格，只有"已确认脉冲"走精细几何 | 事件数增长不影响绘制成本 |
| `EllipsePanel` 绘制设上限（已确认脉冲 512 个） | 噪声记录不会把渲染拖死，且截断会在画面上写明 |

### 12.6 PD 脉冲标注与联动：判据 + 一条必须说清的边界

**判据（两条取较严格者，界面上两个都显示，不做黑盒）**：

1. 用户绝对阈值（默认 **120 AD 码**）。依据：PD 脉冲增量是 +720/+600/+460/+300 码，
   而 DDS 背景相对 2048 的最大偏离只有 42 码（§10.6），120 码能干净地把背景挡在外面。
2. 自适应阈值 `6 × sigma`，其中 `sigma = 1.4826 × MAD`。
   用 **MAD 而不是标准差**，因为标准差会被脉冲本身抬高——而脉冲正是要找的东西。

基线用**中位数**而不是均值：DDS 与真实局放都会让均值偏离真实零点。
中位数与 MAD 都用直方图法在 O(N) 内求出（不需要排序），520,000 点也在毫秒级。

**标注方式**：波形上画竖直标线 + 极性三角标记（正向上、负向下）+ 超出高亮阈值的
用亮色并加端点圆；点选某个脉冲显示幅值/极性/时间读数。椭圆图侧同源同色。

**⚠️ 必须说清的一条边界**：事件包只有 (相位, 幅值, 通道)，DDR 快照只有 (样本码, 通道)，
两者**没有共同的时间戳**，而且 SCOPE 帧与帧之间本来就不连续。
所以两边的联动只能按"**同通道 + 幅值最接近**"互相印证——默认标定下这个匹配有物理依据
（见 §12.3），**但它不是同一事件的时间配对**。界面提示与每次联动的日志都写明了这一点，
文档也不把它说成后者。

另外：波形上无法计算工频相位（没有 sync 信号、没有过零检测），
所以**相位只在椭圆图上给出**，波形标注只给幅值与时间。这也是如实标注，不是遗漏。

### 12.10 需反馈给板端/协作方的三处（累加）

1. **`CONFIG` 应回报每通道 `SCALE`**。现在只在 AXI-Lite `0x10` 有，TCP 侧没有；
   上位机只能手动填、且默认值是占位标定。不回报的话，"pC" 这个标注就只能是相对刻度，
   波形域与电荷域的换算也无法自动对齐。
2. **修正 `pd_feature_core.v` 的位域注释块**（`:555-557`）——它写的是 10 位相位布局，
   与当前配置（12 位）不符，容易让下游按错位移取字段。
3. **`SCOPE` 帧头补 `ring_wr_ptr`（沿用 §7.3）**，这样滚动视图才可能画成真正连续的时间轴。
