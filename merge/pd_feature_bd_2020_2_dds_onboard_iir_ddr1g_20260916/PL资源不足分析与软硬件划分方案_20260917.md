# PL 资源不足分析与软硬件任务划分方案

- 日期：2026-09-17
- 对象工程：`pd_feature_bd_2020_2_dds_onboard_iir_ddr1g_20260916`
- 器件：`xc7z020clg400-2`（Zynq-7020）
- 证据来源：`synth_1/pd_feature_bd_wrapper_utilization_synth.rpt`、`impl_1/runme.log`、BD 网表
  `pd_feature_bd_2020_2.gen/.../synth/pd_feature_bd.v`、BD 脚本 `hw_handoff/pd_feature_bd_bd.tcl`、
  各 IP 的 `.xci`、以及 `imports/rtl/*.v` 源码本身。

## 0. 结论摘要

1. **失效点已实测定位，不是"接近满"，而是 LUT 硬性超容。**
   `place_design` 报 `Place 30-487`：器件 13300 个 slice 中可用 7205，未布局实例需要 7232；
   同一段报告给出 `Luts: 50752 (combined) 59986 (total), available capacity: 53200`
   —— **LUT 总量超出容量 6786 个（12.8%）**。这不是布局器参数问题，必须真实削减逻辑。

2. **优化方向只能是削 LUT，不能动 BRAM/DSP。**
   实测占用：LUT 91.56%、FF 52.77%、**BRAM 30.36%**、DSP 60.00%、
   BUFG 12.5%、MMCM 25%。BRAM 还剩 97 个 RAMB36 没用，这是最大的可腾挪空间。

3. **BD 连接证据表明：滤波 + FFT + 选频整条 DSP 支路，与 PD 事件检测完全并行，不参与实时触发。**
   `pd_feature_bd_bd.tcl` 第 999–1000 行：
   ```
   connect_bd_net -net pd_ddr_0_o_feat_data  [pd_ddr_0/o_feat_data] [pd_feature_0/adc_data] [pd_filter_0/adc_data]
   connect_bd_net -net pd_ddr_0_o_feat_dv    [pd_ddr_0/o_feat_dv]   [pd_feature_0/adc_dv]   [pd_filter_0/adc_dv]
   ```
   即原始 ADC 样本**并联**送给两条支路：`pd_feature_0`（特征提取）与 `pd_filter_0`（滤波→FFT→选频）。
   滤波后的数据既不回喂特征核，也不参与任何触发。**因此右侧整条支路是纯频谱监测旁路，迁移到 PS 不会
   影响局放事件的检出实时性与相位准确性。**

4. **推荐主方向：把右侧整条支路迁到 PS（方案 B）**，PL 只保留"采集 + 相位 + 触发 + 落 DDR"这条
   必须逐样本执行的通路。预计释放 64 个 DSP、约 1.2 万个 FF、1.5 万–2.5 万个 LUT。

5. **必须同时正视 65 MSPS 目标。** 当前 IIR 架构在 130 MHz 下每样本需要 5 个时钟周期
   （`pd_iir_biquad` 的 `PH=5`），26 MSPS 时 `130/26 = 5` 周期恰好打满、零余量；
   若要上 65 MSPS，每样本只剩 2 个周期——**现有滤波链在 PL 内无法工作**。这是支持"滤波迁 PS"
   的最强论据，也是必须在架构上先决策的问题（见 §6）。

### 2.3 资源归因

> 说明：以下分为「RTL 直接算出（确定）」与「按配置推算（待实测确认）」两类，不混淆。

**(a) 由 RTL 直接算出（确定）**

`pd_filter_chain`：
- DSP：每 biquad 例化 2 个并行乘法器（`mul_p_a = mul_a*mul_ca`、`mul_p_b = mul_b*mul_cb`），
  `32 节 × 2 = ` **64 个 DSP48**（占全芯片 DSP 用量的 48.5%）
- FF：每 biquad 状态约 190 位（`prod_a[34] + prod_b[34] + acc[37] + x1/x2/y1/y2[64] + dout[16] + phase[3] + dout_dv[1]`）
  → `32 × 190 ≈ 6080` FF
- 系数双缓冲：`sh_coef[160] + ac_coef[160]`，各 18 位 → **5760 FF**；使能 `sh_en/ac_en` 64 FF
- **滤波链合计：约 1.19 万个 FF，占全设计 FF 用量（56147）的 21%，64 个 DSP**

**(b) 按 IP 配置推算（需用 §7 的 Tcl 精确确认）**

- `4 × XFFT`：`pipelined_streaming_io` 是 XFFT 可选架构中资源最重的一档；配合全 BRAM 存储、
  `use_mults_resources` 复数乘、`natural_order` 输出（需重新排序缓冲），
  是全设计 LUT 的头号消耗者。按总量倒推，4 个 FFT 合计约 68 个 DSP（132 − 64），
  即每核约 17 个 DSP。
- BRAM 42.5 块的构成推算：4×FFT 存储（约 24–32）+ 4×`sin_lut`（约 2）+ 4×`pd_prpd_ram`（约 2）
  + 4×FFT 输入 FIFO（约 8）≈ 42.5，与实际吻合。
- `2 × axi_datamover`（`dm_wr`、`dm_cp`）：DataMover 是高 LUT/FF 消耗 IP，两个实例合计
  估计在 6000–12000 LUT 量级，是仅次于 FFT 的大户。

**(c) LUT as Shift Register 4522 个**

未在自研 RTL 中找到对应的显式移位寄存器代码（`async_fifo.v`、`pd_axis_fifo.v`、`pd_prpd_ram.v`
均已有 `ram_style`/`rom_style` 标注且注释记录过 BRAM 推断修正）。因此这 4522 个 SRL 最可能来自
**IP 内部的延迟链**（XFFT 各级流水延迟线、DataMover 内部缓冲）。
**必须用 §7 的分层报告定位后再决定是否可回收——不要凭推测改动。**

## 3. 实时性分级：哪些必须留在 PL

### 3.1 判断准则

> **唯一准则：该操作是否必须在"采样节拍"上逐样本执行，且不允许丢样或引入非确定性延迟。**

满足则留 PL；只要可以批量、缓冲、事后处理，就是 PS 的候选。

局放检测的特殊性：PD 脉冲上升沿可窄至纳秒级，经 ADC 后表现为单点或数点尖峰；
任何"先降采样再检测"或"先缓冲再检测"都可能漏掉真实放电事件。**这是触发通路必须留在 PL 的物理原因。**

### 3.2 分级结果

| 模块 | 是否逐样本 | 延迟容忍 | 结论 |
|---|---|---|---|
| ADC 采集 / 跨时钟域 FIFO | 是 | 不可 | **PL 必须**（硬件接口） |
| 相位累加器与相位窗（`pd_feature_core`） | 是 | 不可（相位精度依赖样本计数） | **PL 必须** |
| 窗内 max/min、峰值检测 | 是 | 不可（漏样即漏事件） | **PL 必须** |
| 12 档门槛计数、极性判定 | 是 | 不可（与峰值同拍） | **PL 必须** |
| PRPD 直方图累加 | 是 | 依赖相位，同步累加 | **PL 保留**（相位信息在此最准） |
| 8B 事件打包 + AXI DMA | 与触发耦合 | 不可 | **PL 必须** |
| DDR 环形写 / 冻结 / 快照 | 带宽需求（4ch×12bit×26MSPS ≈ 1.25 Gbps） | 不可（PS 经 AXI 拉原始流会挤占带宽） | **PL 必须** |
| IIR 滤波链（32 biquad / 64 DSP） | 是——但**与触发解耦** | 可容忍帧级延迟 | **可迁 PS** |
| FFT ×4 | 否（每 39.4 µs 才一帧） | 充裕 | **可迁 PS** 或 4→1 复用 |
| 选频 bin_monitor | 否 | 充裕 | **可迁 PS** |
| 包络 / 二次统计 / 归一化 | 否 | 充裕 | **可迁 PS** |

### 3.3 支撑结论的量化依据

**PS 侧算力是否够（Cortex-A9 双核 @666 MHz，带 NEON）**

- **FFT**：1024 点复数 FFT（CMSIS-DSP `arm_cfft_f32`）单核约数十微秒量级；
  一帧的时间预算是 `1024 / 26e6 = 39.4 µs`。→ 单核紧张、双核有余。
  若改用 1024 点**实数** FFT，计算量约减半，余量更大。
  **注意**：PS 还要同时跑 Linux 与 TCP/UDP，需实测 CPU 占用后再定。
- **IIR**：每样本每级 5 次乘加 × 8 级 = 40 MAC/样本/通道，4 通道 = 160 MAC/样本。
  26 MSPS 全速即约 4.16 GMAC/s。Cortex-A9 标量峰值约 1–2 GMAC/s，**裸跑不够**；
  但用 NEON 4 路 float32 并行可到约 8 GMAC/s 峰值，**理论可行但负载很重**。
- **关键缓解**：局放事件是**稀疏**的。PS 不需要全时全速滤波，只需在事件窗口（DMA 上报的
  时间戳区间）内对原始样本做后处理滤波。这样平均负载趋近于零，而精度不受影响。
  → **这一条把"滤波迁 PS"从"勉强"变成"轻松"。**

## 4. 软硬件任务划分方案

### 方案 A：最小改动（1–2 天，保全现有架构）

只做"去掉不该有的东西"，不动 DSP 架构。

| 动作 | 预计收益 | 风险 |
|---|---|---|
| A1 移除 `ila_0`（最终综合版不例化调试核） | 1000–2000 LUT + BRAM | 低（保留独立 debug 工程） |
| A2 移除 `pd_dds_0` DDS 激励源，改真实 ADC | 数百 LUT | 低 |
| A3 `dm_cp` 快照复制改由 PS `memcpy` | **3000–6000 LUT + 1000+ FF** | 中低（快照复制变慢，但非实时任务） |
| A4 AXI-Lite 地址位宽由 16 位压到实际需要 | 少量 LUT/FF | 低（需同步改 PS 驱动） |

预期：合计释放约 6000–9000 LUT。**接近但不保证跨过 12.8% 的缺口**，建议作为"止血 + 争取一次布局"。

### 方案 B：推荐主方向（架构级，1–2 周）

**把右侧整条频谱支路整体迁到 PS。**

```
迁移后在 PL 保留：
  采集 → CDC → 相位 → 峰值/门槛 → 事件打包 → DMA → PS DDR
                                            → DDR 环形写/冻结/快照

迁到 PS：
  IIR 滤波（事件窗口内后处理）
  FFT（CMSIS-DSP / 自研定点）
  选频（其实就是在频谱数组上取下标，PS 侧是常数时间）
  包络、二次统计、12 档聚合（如需重算）
```

**为什么会释放大量资源**：
- 释放 `pd_filter_chain`：**64 DSP + 约 11900 FF + 对应 LUT**
- 释放 4 × XFFT：**约 68 DSP + 大部分 FFT 相关 LUT**
- 释放 `pd_fft_input_adapter` 的 4 个 2048 深 BRAM FIFO 与分帧逻辑
- 释放 `pd_fft_bin_monitor_4ch` 的 AXI-Lite 寄存器堆

**预计总释放：132 − 4 ≈ 128 个 DSP（几乎全部）、约 1.5 万–2.5 万个 LUT、约 1.5 万 FF。**
削减后 LUT 预计回到 50% 上下，布局一次性通过。

**代价与必须澄清的契约问题**：
1. 迁移后 PS 需要**原始（或轻量抽取后的）样本流**。当前 PL→PS 只有"事件流"与"DDR 快照"
   两条通路，没有连续原始波形的实时面。**需要新增一条"原始样本 AXI-Stream → DMA"通路
   或约定从 DDR 环形缓存定期读取**。这是方案 B 的主要工作量。
2. 若采用"从 DDR 环形缓存读"的方式，则连 PL 的 `pd_ddr_ring_wr` 都不必改，
   只需 PS 侧驱动按地址窗口读取——**这是最省 PL 的路径**。
3. 需与 PS 侧（黄贵传）重新对齐接口契约：谁负责滤波、谁负责频谱、上报帧格式。

### 方案 C：折中（约 3–5 天）

PL 保留一个**时分复用的单 FFT**（4 通道共享）+ 一个精简 IIR，其余迁 PS。

- FFT：4 → 1。时钟预算核算：130 MHz 下 Pipelined Streaming 吞吐 1 样本/周期。
  4 通道各取一帧共需 `4 × 1024 = 4096` 周期；每通道帧周期为
  `1024 / 26e6 = 39.38 µs`，折算 `39.38 µs × 130 MHz ≈ 5119` 周期。
  **4096 < 5119，理论上余量约 20%，可行。**
- **但必须验证**：`pipelined_streaming_io` 架构在帧与帧之间是否需要额外的流水排空/填充周期。
  若需要，4096 周期的假设不成立，该方案作废。**建议先用仿真确认，不要直接改 RTL。**
- 收益：约 3/4 的 FFT 资源（约 51 DSP + 数千 LUT）。

## 5. 可落地优化清单（按投入产出排序）

### 5.1 立刻可做：把 LUT 里的存储搬到闲置的 BRAM

**这是最被忽视的机会**：BRAM 只用了 30.36%（剩 97 个 RAMB36），
而 LUT 里有 **5440 个被当作存储使用**（4522 SRL + 918 分布式 RAM）。

- 若 SRL 与 LUTRAM 中有哪怕一半是真正可搬迁的缓冲/表，
  仅需数块 BRAM 即可回收 **2000–2700 个 LUT**（约 4–5%）。
- **行动前提**：先用 §7 的分层报告确认这些 SRL 的归属。
  若是 XFFT / DataMover 内部流水线，则不可动，本项作废。
- 对自研模块：检查 `pd_align24_check`、`pd_pack192`、`pd_pack48`、`pd_sync_pulse`
  是否含未标注 `ram_style` 的数组（本次扫描未发现大数组，
  但 `pd_pack192` 的 192 位打包位宽值得复核）。

### 5.2 控制集瘦身（针对 1370 个 control sets）

place 报告明确指出控制集限制了 FF 的打包效率。可做的：
- 统一复位策略：全设计统一为**同步复位**或**异步复位**，避免混用
  （当前报告显示 FF 中 `Reset 29809 + Set 25111 + Async Reset 550`，风格确实混杂）。
- 合并时钟使能域：同一时钟域内尽量共享 `ce` 表达式，减少唯一控制集数量。
- 收益不直接体现为 LUT 数，但能**提升布局可行性与时序余量**，对"差 27 个 slice"的临界失败
  可能直接有效。

### 5.3 RTL 层面：滤波链的编译期裁剪

`pd_filter_chain` 的 8 级 biquad **全部被综合进硬件**，因为
`ac_en[CI]`/`bypass_mask` 是**运行时寄存器**，Vivado 无法优化掉未启用的级。

→ **加一组编译期 parameter**（如 `USE_N_BP`、`USE_N_NT`、`CH_MASK`），
让不用的通道/级在综合阶段就消失。

- 若实际只需要 2 通道 × (1 带通 + 2 陷波)：从 `32 节 + 64 DSP` 降到 `6 节 + 12 DSP`，
  **释放约 52 个 DSP 与 9000 个 FF**。这是 RTL 层面单笔最大的可回收量。
- 注意：旁路 ≠ 省资源。当前 `bypass` 只是数据选择，硬件仍在。

### 5.4 RTL 层面：降低单片滤波的资源密度

`pd_iir_biquad` 每节用 2 个 DSP 并行（`mul_p_a`/`mul_p_b`）。在 130 MHz / 26 MSPS 的
5 周期预算下，要用 1 个 DSP 完成 5 次乘法是做不到的（至少需 5 个乘相位 + 收尾），
**所以不能简单地减到 1 个 DSP**。

可行的替代是**先抽取再滤波**：
- 若先在 PL 做 8:1 抽取（26 → 3.25 MSPS），每样本可用周期从 5 增到 40，
  则 8 级 × 3 乘相位 = 24 < 40，**单个 DSP 即可服务一整条 8 级链**，
  4 通道共享也只需 4–8 个 DSP。
- 代价：只适用于关心的频段在抽取后不折叠的场景（若只看工频附近特征频段，可行；
  若要看高频段放电，不可行）。**需先确定关注的频段范围。**

### 5.5 基础设施瘦身

- `axi_ic_ctrl` 与两个 `axi_smc_hp0/hp1` 的从端口数量复核，能否合并。
- `axi_rs_feature_ctrl_0`（register slice）是否必要。
- `xlconcat_0` 合并中断后的 IRQ 分配。

# 实现

## 6. 必须正视的问题：65 MSPS 目标与当前 IIR 架构冲突

已记录的项目目标包含"真实四通道 AD9226 65 MSPS"，当前验证基线为 26 MSPS。
这两者与现有滤波架构存在硬冲突：

| 项目 | 26 MSPS（当前基线） | 65 MSPS（目标） |
|---|---|---|
| 系统时钟 | 130 MHz | 130 MHz（若要保持） |
| 每样本可用周期 | `130/26 = 5` | `130/65 = 2` |
| `pd_iir_biquad` 需要 | `PH = 5` | `PH = 5` |
| 结论 | 恰好打满，**零余量** | **无法工作** |

即：**现有滤波链在 65 MSPS 下无论如何都无法在 PL 内实现**，除非大幅提高时钟
（7z020 -2 速度等级下 325 MHz 不现实）或下变频抽取。

这与 §5.4 的结论一致，也进一步支持 **方案 B（滤波迁 PS）**：
PS 侧滤波不受 PL 时钟周期预算约束，天然适配 65 MSPS。

**建议作为架构决策项提出，而不是等到上板才发现。**
